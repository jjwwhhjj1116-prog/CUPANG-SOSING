# 기본설정 번들 수량과 신규 URL 초안 연결

## 확인한 차이와 원본 근거

기존 앱의 `bundleEnabled`는 저장만 되고 신규 옵션의 구성 수량에는 적용되지 않았다. 기록된 Couplus 공개 클라이언트 코드 `outputs/step556-couplus-chunk.js`의 `processOptions` → `updateOptionPricing` → `calculateBundleQuantity`와 `outputs/step546-couplus-main.js`의 가격 처리 경로를 읽고 비교했다. 전체 원본 스크립트를 실행하거나 작업 중인 실제 상품을 변경하지 않았다.

원본은 공급 마진액 또는 쿠팡 마진액을 수량 기준으로 선택한다. 단품 CNY 원가 × 환율에서 단품 공급가와 판매가를 반올림해 해당 마진액을 구하고, 목표 마진액을 만족할 때까지 수량을 1, 3, 5…21개로 증가시킨다. UI의 짝수 수량 도움말과 실제 반복문이 달라 실행 코드를 기준으로 구현했다. 신규 옵션 생성 호출은 100원 단위를, 가격 편집·worker 호출은 설정된 가격 처리 단위를 사용한다. 두 경로를 임의로 통일하지 않았다. 최소 공급 마진 보장은 별도 최종 가격 계산에 적용하며 수량 선택 기준에 중복 적용하지 않는다.

이는 저장된 클라이언트 코드 경로의 대조다. 현재 운영 사이트의 모든 카테고리·서버 구현이 동일하다는 증거나 실제 Couplus 번들 상품을 새로 생성해 대조한 결과는 아니다.

## 적용 범위

- 기본설정에 번들 기준과 두 최소 마진액을 추가했다. 번들링은 기본적으로 꺼져 있다. 새 설정의 입력 시작값은 공급 마진액 기준, 양쪽 3,000원이다. 이는 기록된 원본 `settingsData`의 초기값이며 사용자가 번들링을 켠 계정 화면의 관측값은 아니다.
- 새 URL 요청은 당시 설정을 캡처하고 신규 옵션의 구성 수량에 반영한다. 견적 공급가·판매가·MSRP는 저장된 옵션 단품 원가 × 구성 수량에서 기존 가격 엔진으로 계산한다. 원문 SKU·재고·최소 주문 수량은 변경하지 않는다.
- 설정의 가격 미리보기에서도 동일한 신규 상품 수량과 최종 묶음 가격을 표시한다. 예를 들어 3.6 CNY, 환율 350, 공급 50%/쿠팡 40%, 10원 반올림, 최소 공급 마진 보장 3,000원, 번들 공급 마진 기준 3,000원은 3개 구성으로 공급 7,560원/판매 12,600원/MSRP 16,380원이다.
- 기존 상품은 설정 저장만으로 바뀌지 않는다. 옵션 일괄 편집에서 자동 번들 수량을 제안받고 변경 전후 수량·가격을 확인한 뒤 적용·옵션 저장한다. 수량이 달라지면 포장 확인을 다시 요구한다. 수동 견적서 값은 계속 보존한다.
- 구버전의 `bundleEnabled:true`만 저장한 요청은 새 정책으로 소급 변환하지 않는다. 새 세 필드의 누락/null은 기존 미작동 상태로 유지하며 명시적으로 기준을 설정한 이후 요청부터 사용한다.

## 초안 검토 알림

최초 SEO 결과의 AI 검토 경고가 생성 이력에만 저장되고 수집 완료 안내에서는 사라지던 전달 누락을 수정했다. 수집함에서는 중복 제거한 경고 최대 3개·각 200자를 표시하고, 전체 내용은 1단계 생성 이력으로 안내한다. 재사용·옵션 번역 배치·부분 실패에서도 기존 경고를 유지한다. 저장한 경고 원문, 수동 공란·검색어, 생성 결과 적용 조건, 완료 판단은 바꾸지 않았다. 테스트의 경고는 통제된 AI 응답이며 운영 AI가 해당 경고를 생성했다는 관측이 아니다.

## 기존 수집·접수 호환성

새 설정 필드의 정규화만으로 이전 견적서 지문·파일명과 완료 접수 매칭이 바뀌는 회귀를 독립 검토에서 발견했다. 저장된 상품의 견적 출력·7단계 편집·자동화 입력 지문에서 비출력 번들 기준 3개만 제외한다. 실제 옵션 구성 수량, 원본 설정 payload, 캡처 당시 수집 context와 저장 조건은 유지한다. 양사 완료 접수의 동일 견적 ID·6 SKU·재전송 차단, 실제 수량 변경 시 새 지문·기존 출력 409를 검사했다.

이전 수집 요청 재개에서도 기존에 없던 3개 필드 때문에 동일 설정을 충돌로 판단하던 문제를 수정했다. 비교 시에만 누락과 legacy null을 동등 처리하고, 양쪽 번들링이 모두 꺼져 있을 때만 비활성 기준을 제외한다. 활성화·활성 기준/금액·기존 환율 등의 변경은 계속 충돌로 처리한다. 기록된 수집 요청은 수정하지 않는다.

## 검증과 배포

전체 테스트 **2,035/2,035** 통과, 실패·취소·건너뜀 0, 158.220초다. 신규 회귀 22개를 포함한다. 설정 UI, 기록된 상품의 양사 실제 API/임시 SQLite → 6 SKU → 견적/XLSX, 수동 견적 수량·공급가 공란 보존, 신규 수량 선택의 100원/가격 편집의 설정 단위 차이, 저장 중 입력 보호·취소·되돌리기를 확인했다. TypeScript 오류 0, 변경 코드·테스트 26개 파일 lint 오류 0과 기존 `onBusy` 의존성 경고 1, diff·운영 빌드·기존 11개 마이그레이션 원본 일치·Cloudflare 산출물 검사 통과다. TypeScript에서 새 응답의 `unknown` 오류 2개가 발견돼 응답 타입을 명시한 뒤 재검사했다.

최초 운영 빌드는 공용 수집 번들의 소스 일치 검사에서 중단했다. 확장 **0.2.46**을 생성해 원본/ZIP/다운로드 링크를 맞춘 뒤 최종 빌드가 통과했다. 생성 수집 모듈은 203,972바이트로 이전과 크기가 같고, AST 토큰 49,367개의 대조에서 minifier 식별자 재할당 외 비식별자 차이는 없었다. 수집/전송 프로토콜·권한·호스트 변화가 없어 새 capability 제한을 추가하지 않았다. 기존 ZIP을 보존했고 확장 최종 집중 검사 20/20도 통과했다. 이 집중 검사는 전체 검사와 일부 겹쳐 합산하지 않는다.

ZIP은 37파일·449,839바이트이며 소스/운영 산출물 SHA-256은 `c92dbc07363c5bfa47621f65fe9f69382fdbfc079cb3f19059e3a0c4dc9b7e31`로 같다. 기존 `sourceflow` Worker **46c75de5-9e9d-49e0-b3a1-82354a1d7328**에 배포했고 8개 정적 자산 업로드를 확인했다. 배포 후 익명 로그인/새 ZIP 요청은 각각 Cloudflare Access 302였다. 이는 인증 경계 확인이며 로그인한 앱의 시각 검수나 실제 Hub 접수 결과가 아니다. 운영 회원·기존 상품·설정 행·DB 마이그레이션·비밀·유료 자원을 변경하거나 만들지 않았다. `outputs/step570-*` 진단은 Git에서 제외한다.

## 실제 사이트 검증과 구분

직전 단계에서 지정 URL `813724060928`을 실제 수집 함수로 읽어 6옵션·19이미지·24속성을 확인했고, 19개 이미지의 바이트 수신·형식 검사가 통과했다. 이번 변경의 API·임시 SQLite·견적 출력 검사는 그 기록된 원문을 이용한다. 운영 회원 설정이나 기존 상품을 테스트용으로 수정하지 않는다.
