# Step660 — 수집 원가기준과 SEO·견적 초안 범위

2026-10-14. 쿠플러스의 현재 배포 JavaScript와 로그인된 화면을 읽고, 기존 작업 상품을 수정하지 않고 구현을 대조했다. 이번 단위는 원가기준·옵션 SEO·견적 AI 초안 범위의 수정이며, 전체 카테고리 또는 실제 Supplier Hub 등록 완료 검증은 아니다.

## 원가기준

현재 Couplus UI chunk SHA-256 `ce8f14422c4e93a11592d886a369d633066a8a9f4cdba9f37dbb1276d798c6cc`의 `processOptions` UTF-16 구간 [466662,469077), 선택 구간 SHA-256 `4a5671380c795a5b6e598bc3abfcdf54cb66318a62119f43478964ee68b0e3f0`을 대조했다. REA parent는 `ev_1983224a44e1100a435aca7caaa76ebb6e1d9df782252092d57dcc695765e8ee`, summary는 `ev_c09a0b073aa2961fa6660da9d2e95275f34d4826dd950a1c0e9c5abf833a086a`이다. 선택된 12개 inert 메서드의 파싱 실패는 0이며, 외부 import/상태 관계의 의미 분석은 unknown으로 남는다. 공급자 코드는 실행하거나 저장소에 복사하지 않았다.

해당 형식은 SKU마다 truthy `fenxiaoPriceInfo.offerPrice`를 우선하고 없으면 `consignPrice`를 사용한다. 원래 전체 SKU 가격이 같으면 원문 `productSaleInfo.priceRangeList[0].price`를 사용한다. 선택 옵션 subset, 최저가격 또는 수량별 구간을 기준으로 바꾸지 않는다.

YOOFAM의 기존 OpenAPI 후보 파서는 `sku.price`만 읽었다. 새 `alibaba-source-pricing`은 위의 명시적인 응답 형식에서 원가를 선택하고, 원래 각 SKU 가격·출처·첫 기본가격·선택 규칙을 `CollectionResult.priceBasis`에 보관한다. 수신·저장·재조회 시 정확한 SKU 순서, 자료형, 양수 가격, 규칙과 실제 옵션 원가의 일치를 재검사한다. 원문 확인 화면은 보관한 SKU 가격과 견적 원가를 비교 표시한다.

기존 explicit `sku.price` 후보의 호환 분기는 유지한다. 모바일 `skuParam`의 수량별 가격과 공개 JSON-LD에는 새 선택 규칙을 적용하지 않는다. 불완전한 consignment 응답, 유효하지 않은 선택 가격이나 첫 기본가격은 오류로 반환하며 다른 가격을 임의로 대입하지 않는다. 숫자 0·빈값과 문자열 `"0"`의 원문 truthiness 차이를 보존하되 유효하지 않은 가격을 성공 처리하지 않는다.

두 회사의 실제 로컬 handler·SQLite 검사에서 원문 SKU 25.6이 동일할 때 첫 기본가격 5.23으로 초안을 만들고, 서로 다른 SKU 가격은 유지하는 것을 확인했다. 원래 receipt 가격 기록은 초안 생성 후에도 보존한다. 이것은 합성 원문 검수이며 현재 계정의 실제 OpenAPI 접근·실상품 수집 증거는 아니다.

## 옵션 SEO와 견적 AI

- 옵션 SEO 상품명 100자·검색태그 150자 입력 제한과 카운터를 추가했다. 연결 양식의 제한이 더 작으면 더 작은 값을 사용한다. 이전에 저장한 긴 문자열을 잘라내지 않으며 초과 저장을 막는다. 직접 공란·자동값 복원·동시 변경·응답 불확실 복구 동작은 유지한다.
- 기록된 Couplus 견적 AI의 기본 범위와 같이 모든 포함 옵션 작성을 기본으로 한다. 화면 진입 자체는 조회만 수행한다. 저장된 전체 옵션 초안은 개별 옵션 화면에서도 다시 검토할 수 있고, 전체 범위를 해제하면 선택 옵션의 제안만 미저장 입력에 적용한다. 공급자 재호출이나 자동 상품 저장·전송은 발생하지 않는다.
- 같은 카테고리의 진행 중·불확실 실행은 다른 옵션 또는 수정된 초안에서도 확인할 수 있다. 범위를 바꿔 중복 실행하지 않으며, 오래된 제안을 현재 입력에 적용하지 않는다.

일반 상품추가의 원문 흐름은 수집·양식 연결·저장 후 SEO와 가격 계산이다. 큐의 전체 작업·전송 분기는 별도다. 기존 브랜드·특징·타겟 반영은 현재 초기 번역 적용 경로에 이미 있으므로 중복 구현하지 않았다. 실제 Gemini 최적화 출력과 쿠플러스 비공개 수집 서버의 동작은 이 정적 조사로 동일하다고 주장하지 않는다.

기본설정·가격 계산 72개 검사는 저장된 회사별 값과 현재 초기 최소마진 하한 경로를 확인했다. 초기 작업과 명시적인 2단계 재계산의 고정 최소마진 경로를 섞지 않는다. 현재 사용자가 저장한 환율·박스 수량을 신규 계정 기본값으로 덮지 않았다. 기존 가격 UI 시험의 누락된 React layout effect stub만 바로잡았다.

## 검수와 배포 산출물

관련 검사 360개 통과: 견적 AI 70, 설정·가격 72, 원가·수신 계약 33, 소스 상호운용·옵션 SEO 84, 확장 38, DB 초기화·기본 가격·자동화·스키마 63. 중복 재실행은 합계에 다시 더하지 않았다. 실패·중단·skip은 0이다. 핵심 변경 파일 lint에 오류가 없고, 다운로드 링크 파일 검사에는 기존 intake callback 의존성 경고 1개가 남는다.

같은 로그인 Chrome의 실제 React 화면에서 두 회사·두 옵션을 합성 데이터로 검사했다. 전체 초안 조회·선택 옵션 적용과 원문 9위안에서 첫 기본가격 6.1위안을 선택한 표시를 확인했다. 공급자 호출·상품 저장·Hub 제출은 0이다. 네 개 DOM proof의 최종 source hash를 보관한다. 최종 가격 화면 screenshot은 캡처 시간 초과로 저장되지 않았으며, 이미지 검수 성공으로 보고하지 않는다.

공유 receipt validator 변경으로 MV3 수집 번들도 다시 생성해야 했다. 확장과 다운로드 링크를 0.2.72로 맞췄고 기존 0.2.71 ZIP은 보존했다. 새 ZIP은 52파일·703,341바이트, SHA-256 `9a3d65b037625b157ea03b7e157ae6e20862050c5bff0bd0adf736d3a5083ce5`이다. 호스트 권한과 개별 등록 실행 게이트는 바꾸지 않았다. ZIP 생성은 사용자의 Chrome에서 새 버전이 실행 중이라는 증거가 아니다.

최종 운영 build 및 산출물 검사 통과. 수정본은 기존 Worker에 배포했고 최종 버전은 `316d3b04-e8f6-4a21-bae2-62f8d89e854c`이다. 아래 한도 제한으로 운영 목록의 사후 정상 조회는 미확인이다. DB 마이그레이션이나 기존 상품 원가 재계산은 수행하지 않는다.

## 운영 조회 제한과 반복 초기화 감소

최초 배포 `0d00a41c-5006-4c7c-859a-52b5a6c79a4a` 뒤 같은 Chrome에서 목록 조회가 500/503으로 실패했다. 직전 정상 버전 `78b0c55d-9280-4aec-b462-8966e466ab44`로 복구해도 같은 오류가 재현됐다. Worker는 요청을 처리했지만, 잡힌 서버 오류에 D1 무료 플랜의 **일일 row-read 한도 초과**가 명시돼 있었다. CPU 초과나 이번 가격 변경이 원인이라고 보고하지 않는다. 한정된 설정 GET 진단을 배포해 원인을 확인한 후 임시 로깅 코드는 제거했다.

[Cloudflare D1 요금 문서](https://developers.cloudflare.com/d1/platform/pricing/)는 Free의 하루 500만 읽기 행, UTC 00:00 초기화와 한도 초과 시 조회 오류를 명시한다. 현재 확인 시각은 2026-10-14 UTC이며 다음 초기화는 한국시간 2026-10-15 09:00이다. 플랜 변경·새 DB·인증 완화·한도 우회 경로는 추가하지 않았다. 계정 전체의 실제 소비처별 비중은 아직 측정하지 않았다.

`db/queries.ensureDatabase`는 성공적으로 완료한 초기화만 D1 바인딩별 `WeakSet`에 기억한다. 상품·설정·로그인 데이터는 캐시하지 않는다. 요청 사이의 진행 중 I/O promise를 공유하지 않으며 초기 실패는 다음 요청에서 재시도한다. 기존 일곱 개 테이블·인덱스 선언은 그대로 유지하고 매 온라인 조회의 `PRAGMA optimize`를 제거했다. 다른 DB 모듈의 초기화나 새 isolate의 첫 초기화까지 제거한 것은 아니며, 이 수정으로 이미 초과한 한도가 복구된다고 주장하지 않는다.

기존 작업 상품 한 건은 관리 API의 읽기 전용 검사로 배포 전 DOM의 등록번호·상품명·옵션 6개·공급가 4,260원·판매가 7,100원과 대조했다. 값이 같고 마지막 수정 시각은 이번 작업 전이었으며, 검사 쿼리의 `changes`와 `rows_written`은 0이다. 이는 운영 UI의 사후 정상 조회나 대기열 보존 검증을 대신하지 않는다. `uiPostDeployVerified`와 UI 상태 비교는 미확인으로 남긴다.

개발용 출력·배포 산출물은 `tsconfig`의 프로젝트 파일 검색에서 제외했다. 실제 앱·DB·배포 소스의 검사는 유지한다. 한정된 heap으로 실패한 TypeScript 실행은 타입 검사 통과 근거로 사용하지 않는다. 최종 `tsc --noEmit`은 heap 1,536MiB에서 오류 없이 통과했고 핵심 변경 파일 lint도 오류·경고 0이다. DB 초기화 수정 뒤 두 회사 원가 저장·URL intake 23개도 재실행해 통과했으며 360개 합계에 중복 가산하지 않았다.

## 남은 전체 워크플로 검수

실제 새 URL의 전체 SKU·이미지 수집, 모든 카테고리의 기본값과 1~7단계 동일 출력, 새 Supplier Hub 문서의 최종 동의·접수·SKU 확인은 미완료다. OpenAPI 후보 파서 지원을 실제 인증 연결 또는 수집 성공으로 표현하지 않는다. 운영 개별 등록 게이트는 `false`를 유지한다. 기존 작업 상품을 수정하거나 이전 접근 차단을 다른 제어 수단으로 우회하여 이 검수를 대체하지 않았다.
