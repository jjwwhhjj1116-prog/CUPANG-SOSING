# 보관된 접수 결과에서 Supplier Hub 조회 복구

2026-10-01, 543단계.

## 수정한 문제

542단계에서 앱의 접수 결과 복원과 접수 ID 고정 추적은 연결됐지만 Chrome 확장은 자신의 로컬 검증 기록과 원래 전송 탭 연결을 요구했다. 원래 탭을 닫거나 로컬 기록이 없는 경우 앱에 올바른 접수 ID가 보관돼 있어도 상품별 SKU 조회를 재개할 수 없었다.

## 최종 동작

- 요청한 원래 앱 탭의 content script가 같은 출처의 회원 소유 접수 API를 읽는다. 검증 완료 상태, 접수 ID, 회사, 파일명, 옵션 수, 카테고리, 폼, 확인값과 관찰 시각을 검사한다. 현재 저장한 견적서의 확인값·폼·회사·포함 옵션 수가 같아야 복구할 수 있다.
- 앱의 `quotation` source 응답에 포함 옵션 수를 추가했다. XLSX 재생성이나 이미지 다운로드 없이 현재 저장본과 전달 파일의 옵션 수를 대조한다. 원본 앱의 정확한 탭/창/출처와 최근 응답 시각도 검사한다.
- 기존 로컬 결과가 잘못됐으면 서버 결과로 덮어쓰지 않는다. 정상 로컬 결과와 서버 결과의 접수 ID·회사·파일·옵션 수가 다르면 중단한다. 로컬 결과가 없는 복구는 IndexedDB 원자적 claim으로 처리해 동시에 들어온 다른 기록을 덮어쓰지 않는다.
- Chrome 조회는 요청한 앱과 같은 창의 Supplier Hub 등록/견적 조회 URL만 대상으로 한다. 해당 화면에서 회사코드를 확인하고 새로운 비활성 견적 조회 탭을 준비한다. 다른 수동 검색과 기존 첨부 화면은 그대로 둔다. 복구한 전용 조회 탭은 이후 재사용한다. 새 Chrome 창/프로필을 만들지 않는다.
- 복구한 과거 SKU 행을 새로운 조회의 증거로 복사하지 않는다. 실제 조회된 페이지의 행만 저장하며 조회 중 앱의 저장본·회사·접수 ID가 바뀌면 새 결과를 저장하지 않는다.
- 복구된 접수 결과만 있고 업로드 claim이 없어도 앱과 팝업은 다시 첨부하지 않는다. worker도 이를 `not-started`로 반환하지 않는다. 조회 복구를 위해 전송 시도 기록을 만들어내지 않는다.
