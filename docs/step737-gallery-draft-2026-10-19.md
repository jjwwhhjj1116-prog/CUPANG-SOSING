# Step737 — 갤러리 사진과 SKU 사진의 초기 배치 구분

카테고리·URL 수집 결과가 1~7단계 초안에 반영되는 경로를 이어서 검수했다. 기존 작업 상품과 회사 설정은 변경하지 않았다. 신규 구조화 상품 원문에서 갤러리에 없던 SKU 사진이 공통 추가이미지 초안에도 들어가는 차이를 수정했다.

## 원본 대조

REA 보관 분석과 현재 보관 route의 `processOptions`를 대조한 결과, 원본은 초기 추가이미지 후보에 `productImage.images`를 보관하고 첫·둘째 SKU 속성 사진과 선택 대표 사진은 별도로 보관한다. 자체 parser는 사진을 파일풀에 합친 뒤 원래 갤러리 출처를 잃어 SKU 후보도 공통 추가 배치에 선택했다.

현재 원본 범위는 UTF-16 `[467246,469661)`, slice SHA-256 `3b006f4f7a14b17fcdaf1846dc7fbb3717ae87b35952a86bbc7bbf2af672f5bb`다. 보관 parent는 `ev_5869fb5a1a6ec67485ac76e74414a221ecb4eb7a035d0344c07e66b28c7bcec2`다. 정확한 파일·범위·보조 hash·관측 한계는 [독립 원본 감사](step737-intake-parity-audit.md)에 기록했다. 새 producer, vendor 실행과 네트워크 요청은 하지 않았다.

이 근거는 원본의 초기 후보 출처에 관한 것이다. 첫 갤러리 사진을 최종 견적의 추가이미지에 다시 넣어야 한다는 뜻은 아니며, 원본 Stage4 전체 동작과 실제 수집 실행을 새로 관측한 결과도 아니다.

## 반영한 계약

- 신규 OpenAPI 후보 parser에서 갤러리 등록 직후 `sourceGallery:{format:'1688-openapi-gallery-v1',imageIndices:[...]}`를 보존한다. 중복 URL을 기존 파일 번호로 재사용한 뒤의 원래 갤러리 순서다. SKU 후보·대표 번호·원가·MOQ·재고·상세 순서는 바꾸지 않는다.
- 선택적 marker는 OpenAPI 후보 및 그 원문에 파일만 덧붙이는 보완 provider에서 검증한다. 정확한 키, 자료형, getter 없는 객체/배열, 1~200개의 조밀한 정수 prefix, 첫 main·나머지 additional 역할을 검사한다. 잘못된 marker를 추정으로 복구하지 않는다.
- 출처 marker가 없는 기존·모바일·JSON-LD 기록에는 marker를 추정하거나 소급 추가하지 않는다. 기존 공통 배치 동작도 유지한다. 원본 보완은 원래 갤러리 prefix와 SKU 번호를 보존하며 덧붙인 파일을 원래 OpenAPI 갤러리로 표시하지 않는다.
- 갤러리 밖 SKU 사진도 모두 원본 자료함에 저장하고 해당 SKU의 대표 연결을 유지한다. 새 marker가 있는 경우에만 공통 추가이미지의 자동 선택 대상에서 제외한다. 순차 저장, 저장한 파일 재사용, 작업용 이미지 초안에 같은 판정을 적용했다.
- 공통 배치 허용 여부는 기존 옵션 대표 연결 flag와 분리했다. 의도적으로 공통 추가 배치에서 제외한 후보에는 미배치 경고를 내지 않으며 실제 SKU 연결 실패 경고는 유지한다.
- 사용자는 전체 자료함에서 SKU 후보를 공통 이미지로 직접 선택할 수 있다. 명시적인 선택·공란·번역/생성 이미지·제외 옵션·분리 파일은 기존 보호 규칙을 유지한다. 파일 수와 배치 제한, 회사 소유권 및 저장 시점 동시성 검사도 그대로다.

두 회사의 실제 로컬 API/SQLite 검사에서 신규 marker와 marker 없는 이전 원문을 각각 저장·순차 import·재사용·견적 반영·수동 수정·원문 재처리했다. 추가이미지는 새 원문에서 갤러리만, 이전 원문에서는 종전 정책대로 연결됐고, 양쪽 모두 SKU 대표 사진과 모든 원본 파일은 보존됐다. 이미 수집된 기록을 운영에서 새 형식으로 바꾸는 마이그레이션은 없다.

## 검수 범위와 남은 경계

독립 검수의 격리 단언은 9/9 통과했고 조사한 소스 8개의 SHA가 실행 전후 같았다. 별도 초기 단계 흐름 검사 10/10 및 이미지 집중 검사 10/10은 최종 회귀 검사와 겹치므로 합산하지 않는다. 초기 집중 검사의 실패 세 건은 VM realm 배열 비교와 legacy 경고의 종전 동작에 대한 검사 기대값을 바로잡은 뒤 통과했다.

신규 URL의 실제 1688 취득, 비공개 상품 공급자, 모든 카테고리의 현재 양식과 최종 native POST/ACK·새 실제 접수는 여전히 미검증이다. 기존 사이트 안전 거절을 재시도하거나 다른 경로로 우회하지 않았다. 두 native live 검증 flag는 false다. 이번 소스 배치 수정이나 합성 접수 검사를 전체 복제·실제 접수 완료로 표시하지 않는다.

## 최종 검사와 배포

관련 24개 파일 **209/209** 통과, 실패·취소·생략 0. 소스 1,367개의 SHA가 검사 전후 및 빌드 후 일치했다. 타입 검사와 변경 파일 lint는 오류·경고 없이 통과했고 운영 빌드·공유 모바일 모듈 재생성 일치 검사·ZIP 검사도 통과했다. 증거는 outputs/step737-related-final-{freeze,proof}.json, step737-final-validation.json과 개별 검사 로그다.

기존 Worker sourceflow에 배포했다. 버전은 `6db931a5-7695-46b4-b5ab-8e2bb25d6094`다. 기존 환경값과 DB 구조는 유지했다. 준비 확장은 **0.2.85**, 60파일, 754,393bytes, ZIP SHA-256 `3f1fbeaffb7b50ab4bb326d9c3edbfacc082bae7af2e80b491a5e897d502dc61`다. 공유 수집 검증기 변경을 반영해 모듈을 재생성했으며 manifest 권한·호스트·content script는 바꾸지 않았다. 설치된 Chrome 확장이 이 버전인지 확인하거나 갱신한 것은 아니다.

배포 후 기존 Chrome4의 자체 앱 화면을 새로고침해 관리자 로그인·기존 상품 1건과 대기열 배지 1건이 유지되는 것을 확인했다. 기존 상품 편집·삭제·작업 개시·등록 전송은 실행하지 않았고 원래 Couplus/Hub 작업 탭도 조작하지 않았다. 화면은 outputs/step737-deployed-dashboard.png다. 새 실제 원문 수집·Hub 접수의 증거로 세지 않는다.
