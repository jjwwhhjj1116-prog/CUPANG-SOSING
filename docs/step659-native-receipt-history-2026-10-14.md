# Step659 — 개별 전송 확인 결과 보관과 등록상태 연결

개별 문서에서 조회한 등록 파일 결과를 서버에 보관하고 상품 목록·7단계 확인 이력에 연결했다. 기록을 읽는 것만으로 전송 세션, 동의 또는 제출 요청을 복원하지 않는다. 기존 편집 상품은 변경하지 않았다.

## 구현 범위

- `supplier-hub-single-receipt` API는 승인된 현재 회원 회사와 현재 상품·옵션·카테고리의 준비 자료를 다시 계산한다. 현재 자료와 다른 식별값·본문 해시·이미지 연결·회원정보는 저장하지 않는다. Supplier Hub를 호출하는 API가 아니라 Chrome 관찰 결과의 보관 API다.
- `supplier_hub_single_receipts`는 기존 XLSX 전송 기록과 별도로 보관한다. 상품 입력의 버전을 수정하지 않으며, 원래 요청·문서·등록 파일의 값과 원문 자료 식별값을 유지한다. 회원·원문·견적 수정 버전은 SQL 쓰기와 반복 요청 조회 안에서도 확인한다.
- 신규 관찰은 기존 기록만 갱신한다. 오래된 같은 결과를 다시 저장해도 새 문서가 생기지 않는다. 문서·등록 파일의 번호/문자열 타입 변경, 다른 상품의 요청번호 재사용, 완료 후 진행중으로의 역행, 반려 기록의 부활은 허용하지 않는다.
- 기록 순서는 서버에 처음 보관된 전송 순서를 따른다. 오래된 문서의 조회 시각이 갱신돼도 나중 전송보다 앞으로 옮기지 않는다. 한 초안에서 실제 기록된 옵션 수만 표시한다.
- 저장 확인이 유실되면 같은 관찰 결과의 **앱 저장만** 다시 시도한다. Supplier Hub 제출은 반복하지 않는다. 저장이 확인된 뒤 목록의 등록상태만 새로 읽으며, 현재 입력·가격·이미지·견적 세션은 다시 불러오지 않는다. 늦은 상태 조회가 새 결과를 덮어쓰지 않는다.
- 새로고침 후 기록은 읽기 전용으로 표시한다. 현재 저장 버전과 이전 저장 버전을 구분하고, 내부 옵션 UUID 대신 확인 가능한 옵션명 또는 이전 옵션 기록으로 표시한다.
- 목록에서 기존 파일 전송과 개별 문서 전송을 함께 확인할 수 있다. 문서 ID와 등록 파일 ID는 따로 표시한다. `FINISHED`는 등록 파일 처리 완료이며 이 단계에서 SKU 등록 완료를 주장하지 않는다.
- 진행중·처리완료 기록은 삭제와 최초 원문 덮어쓰기를 막는다. 전체 이력 읽기 실패·손상·범위 초과는 삭제 가능으로 바뀌지 않는다. 삭제 검토 이후의 기록 추가·갱신도 SQL 단계에서 다시 검사한다.

## 관찰된 외부 계약과 경계

이전 REA 분석의 Supplier Hub 번들 SHA-256 `6fc9c0fae51702e62e2d1376ac8854d0d97c0035b0bf96afeb42069c2a5abe11`을 기준으로 기존 Step658 계약을 사용했다. 신규 업체 코드나 공급사 기본값을 추정하지 않았다.

`/sr/draft/api/drafts/register-requested`의 `SUBMITTED`·`FINISHED`·`REJECTED`와 원래 `docId`·`qvtRequestId`의 연결을 보관한다. 해당 API의 등록 파일 처리와 별도의 SKU 발급은 구분된다. 정적 코드 분석과 합성 실행 검사를 실제 신규 상품 접수 증거로 취급하지 않는다.

## 운영 반영

Worker `78b0c55d-9280-4aec-b462-8966e466ab44`를 기존 서비스에 배포했다. DB/이미지 저장소/인증/무료 번역 및 AI 공급자는 유지했다. CLI D1 import는 OAuth 인증 오류로 실행되지 않았으며, 앱의 기존 DB 초기화 경로가 추가 테이블을 생성했다. 배포 후 인증된 앱에서 필요한 테이블 존재와 DB 읽기 성공을 확인했다. 기존 상품과 복구된 입력 두 행을 읽기 전용으로 대조했다.

확장 코드는 변경하지 않았고 준비된 배포 파일은 **0.2.71**이다. 운영 Chrome에서 실제 실행 중인 확장은 **0.2.64**로 확인됐다. 개별 문서의 새 연결을 실제 검수하려면 기존 확장을 최신 폴더로 다시 로드해야 한다. 이번 화면·서버 저장 수정의 배포를 확장 업데이트 완료로 보고하지 않는다.
