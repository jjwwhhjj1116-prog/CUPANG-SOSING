# Step674 — 상품추가 시 카테고리·기본설정의 동일 시점 보존

기준은 Step673 `b0710921497cc46a941f0449d30d16eb6fabd01f`다. 이번 변경은 카테고리 선택 → URL 입력 → 수집 대기열 접수 사이에서 카테고리 양식과 기본설정이 바뀌는 경우를 처리한다. 기존 작업 상품이나 쿠플러스 저장값은 변경하지 않았다.

## 확인한 문제와 수정

기존 접수 API는 선택 카테고리 버전과 기대 기본설정을 읽어 확인했지만, 이후 대기열 저장 transaction에는 같은 값을 확인하는 조건이 없었다. 확인 직후 다른 요청이 카테고리 양식 또는 기본설정을 바꾸면 이전 값으로 접수가 성공할 수 있었다.

카테고리의 해석된 값과 원본 payload를 같은 owner-scoped SELECT에서 읽는다. 대기열 저장 transaction의 모든 claim 삭제·이전 claim 연결·새 요청·context·claim 저장·결과 조회에 owner, 카테고리 ID·revision·원본 payload와 기본설정 payload 조건을 적용한다. 기본설정 행이 없던 경우에도 없다는 조건을 확인한다. 설정이 바뀌면 기존 conflict code의 409로 응답한다. 완료 뒤 별도 조회를 통해 성공을 실패로 오인하지 않도록 conflict 판단 역시 같은 transaction의 결과를 사용한다.

카테고리 변경 409를 받은 상품추가 시작 작업은 해당 행에 오류를 표시하고 다음 행 전송을 멈춘다. URL, 특징, 키워드와 선택한 카테고리를 유지하며 자동으로 다른 분류를 선택하거나 다시 수집하지 않는다. 최신 카테고리 선택 또는 기본설정 재조회 후 사용자가 다시 시작한다. 기존 수집 요청의 최초 context·중복 방지·회사 분리 규칙과 내부의 기존 3인자 호출 계약은 유지한다.

## 원본 대조의 범위

지정한 기존 Chrome의 쿠플러스 `/AIRocketReg`와 Supplier Hub를 읽었다. 두 화면의 현재 회사는 유앤채다. 쿠플러스 기본설정에는 일반 환율 350원, 통합통관 환율 290원, 공급·쿠팡 마진 50%·40%, 최소 공급 마진 3,000원, 10원 반올림, MSRP 1.3배가 표시됐다. 사용 중인 계정의 설정을 보편적인 기본값으로 간주하거나 다른 회사에 덮어쓰지 않았다. 원본 설정 화면의 DOM은 ignored `outputs/step674-couplus-settings-dom.txt`에 보관했다. 해당 화면의 screenshot은 CDP timeout으로 생성되지 않았다.

보관된 가격표 artifact도 REA로 추가 대조했다. Evidence `ev_b7a8f6feaa7c516dde6a028fe0b52d6b91407eddd0853e6ffcf0f14fa27377c4`, 기존 `ev_80058b8130c110cfd1ec44a0c48cf2441311a5ce02c3a66e52f40c0fbf65b42f`·`ev_cd5b12712ef6b71c2acfc13858957b76b067e15d1319aac6ac68b3c3a642258a`를 사용했다. 기본 정렬 없음, 옵션번호 정렬 비활성, 최대 세 키·복사 배열 정렬을 확인했다. 한글 header key와 영문 행 필드의 불일치 때문에 실제 가격 값 정렬 여부는 미확정이다. 미보관 Vuetify 코드에 의존하는 헤더 클릭 주기도 미확정으로 남겼다. 추정으로 기능적인 값 정렬을 새로 넣지 않았다. ignored `outputs/step674-price-sort-audit/`에 9개 구문 분석 성공, 범위·digest·근거를 보관했다. 정적 분석은 실제 서버 저장 또는 실행을 관찰한 증거가 아니다.

## 검수 결과

실제 API와 임시 SQLite를 사용해 카테고리 revision 변경·같은 revision의 payload 변경·원문 바이트 변경·삭제, 기본설정 변경·삭제·없음에서 생성, 정상 접수·중복 재시도·COMMIT 이후 설정 변경과 transaction 중간 실패를 검사했다. 기존 claim 해제와 과거 요청 연결을 포함해 실패 시 jobs·context·claims가 그대로 남는지 대조했다. 대기열 모델 검사는 두 회사에서 첫 카테고리 충돌 뒤 추가 POST·수집·작업 공개가 없고, 입력·선택·뒤 행이 보존되는지 확인했다. 기존 일반 입력 오류의 후속 행 처리와 기본설정 재조회 동작도 유지된다. 최종 소스의 관련 **12파일 131개**가 통과했다(백엔드 85개, 대기열 46개; 서로 중복 없음). 전역 TypeScript, 변경 파일 ESLint와 최종 Worker 빌드도 통과했다. 독립 코드 검토의 미해결 지적은 없다. 기존 category-identity mock은 원문과 해석값을 함께 반환하는 새 내부 조회 계약에 맞췄으며, 기존 검증 단언은 바꾸지 않았다. 초기 mock 실패와 수정 후 재실행을 추가 통과 개수로 합산하지 않았다.

지정한 동일 Chrome에서 실제 IntakeQueuePanel·CategoryPicker·접수 API와 임시 SQLite를 사용했다. 와이홉은 접수 직전 카테고리 v1→v2 변경을 주입했고 첫 요청 409, 두 번째 행 입력 대기, jobs·context·claims 불변을 확인했다. 입력을 유지한 채 최신 카테고리를 선택하자 기존 갱신 안내가 나타났고, 재확인 후 v2로 선택한 행만 수동 재시작해 200으로 접수됐다. 유앤채는 저장 직전 환율 350→351 변경으로 첫 요청 409와 후속 행 중단을 확인했다. 최신 기본설정을 다시 불러온 뒤 수동 재시작한 두 행은 351원 설정으로 각각 200 접수됐다.

총 POST 5회는 충돌 2회와 정상 대기열 접수 3회다. 네 DOM 상태의 URL·특징·키워드·선택 유지, 저장 context의 회사·카테고리 ID·revision·기대 설정과 실제 설정, 기존 합성 원문과 소스 파일 hash를 대조했다. ignored `outputs/step674-native-{dom-proof,proof,verification}.json` 및 재현 서버·검증 스크립트에 보관했다. 실제 회원 인증·카테고리 카탈로그·수집 경계는 합성 fixture이며, 실제 1688 수집·번역·업로드·Supplier Hub 전송을 수행한 증거가 아니다. collector 경계에서 의도적으로 중단하므로 접수를 상품 초안 완성으로 표시하지 않는다. 외부 요청·운영 DB 쓰기 0, 최종 sourceFrozen=true다. PNG 촬영은 두 검수 상태에서 CDP timeout으로 실패했다. 자체 검수 탭·loopback 3664 서버는 종료했으며 원본 쿠플러스 기본설정 패널은 저장 없이 다시 접었다.

## 운영 반영과 전체 작업 범위

새 migration은 필요하지 않다. Step669의 `0024_product_registration.sql` 원격 적용 및 Step669 이후 코드 배포는 Cloudflare 인증 완료를 실제로 확인하기 전까지 미완료다. 운영 Worker의 마지막 확인 버전은 Step668 `c9f47c1e-9d46-49c7-8eb4-fef0f70d8021`이다. 이번 작업에서 새 OAuth 요청이나 만료된 동의 클릭, 보안 완화·유료 자원 생성은 하지 않았다.

새 1688 상품의 전체 SKU·이미지 수집, 모든 카테고리의 실제 공식 양식·기본값, 나머지 단계 UI와 Supplier Hub 동의·최종 접수 번호·SKU 대조는 여전히 전체 완료 조건이다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`, 운영 mutation gate=false를 유지한다. 과거 읽기가 거절된 URL을 다른 도구로 우회하지 않았으며 임의 완료율을 산정하지 않는다.
