# Step683 — 저장 전 개별 상세 사진 보관·다시 편집

기준 `a993e22d11b90eabec2660d72bf1730fb57159f0`. Step682의 최종 통합 PNG 복사 다음에, 해당 PNG를 만들 때 사용한 개별 사진의 순서를 함께 보관하고 대상 옵션에서 다시 편집하는 경로를 구현했다.

## Couplus 대조와 범위

`docs/step683-detail-editor-parity-audit.md`에 보관된 JS의 SHA·정확한 소스 범위·retained Evidence와 합성 반례 8개를 정리했다. 외부 사이트·실상품·1688에 새로 접근하지 않았다. 정적 코드는 서버 실행 성공의 증거가 아니다.

Couplus는 최종 견적 이미지 외에 root 편집 HTML과 처리 그룹을 따로 보관하여 재오픈한다. 최종 PNG만으로 개별 사진·원본/가공 연결·OCR 영역을 역으로 복원할 수 없다. 현재 앱의 전역 `ProductContent.assets/detail`을 복사하면 다른 카테고리의 자동값도 달라지므로 이번에는 **실제 상세 저장 영수증의 봉인된 입력 사진**을 카테고리별 별도 자료로 연결했다. 당시의 순서·키·SHA256·표시 크기·출력 PNG와 원래 상품/옵션/저장 번호를 유지한다. 오늘의 전역 역할을 과거 저장 입력으로 바꾸어 쓰지 않는다.

이는 다시 개별 사진을 열어 순서·삭제·편집·재번역으로 이어가는 기능이다. Couplus의 임의 root 리치 HTML, 이전 OCR 좌표·폰트·브러시/undo, 원본→번역 그룹 전체의 완전 복제는 아니다. 타 서비스 requestId나 번역 성공 기록을 새 대상의 처리 증거로 만들지 않는다.

## 구현

- `saved-detail-inputs-v1` 자료는 엄격한 필드·소유 키·출력 업로드 번호·카테고리·원래 identity를 검증한다. 입력 사진 1~150장, 각 표시 크기 1~16000/40Mpx, 통합 높이 16000px와 파일 한도를 지킨다. 같은 사진의 중복 **위치**는 조용히 없애지 않는다.
- 상세 적용 창의 `저장 전 개별 사진 N장도 함께 보관해 다시 편집하기`로 선택한다. 미리보기에서 사진 수와 교체할 현재 카테고리 편집 목록을 확인한다. 새 `editorPolicy`를 요청·미리보기 지문·영수증에 묶었다. 기존 정책 없는 요청과 대기 중인 옛 영수증은 견적 이미지 전용으로 유지하여 승인 범위를 확대하지 않는다.
- 새 정책에서만 대상 이미지 풀에 없는 입력 키를 추가하고 `QuotationFieldsState.detailEditorInputs[categoryScope]`에 별도로 보관한다. 원본 상품·다른 대상·다른 카테고리·전역 콘텐츠/역할·옵션·표시사항·가격·수집 원문과 작업 identity는 유지한다. 새 일반 상세 저장은 해당 카테고리의 이전 복사 자료만 정리하고 새 자체 영수증에서 입력을 읽는다.
- 미리보기·저장 직전·새 정책의 재조회에서 실제 PNG와 입력 사진들의 해시·표시 크기·총 30MiB 한도를 확인한다. 비동기 파일 검사 뒤 모든 원문 스냅샷도 다시 확인한다. 기존 원자 batch·부분 실패 롤백·512KiB 견적/2MiB 기록 한도를 유지하며, 19대상도 **97 SQL문 / 최대 20바인딩 / 최대 13,446 SQL바이트**다. 새 테이블은 없다.
- 대상의 `저장 전 개별 사진으로 편집`은 현재 옵션의 통합 이미지가 해당 자료와 일치할 때 표시된다. GET으로 최신 저장본과 모든 파일을 검증한 뒤 **로컬 입력만** 채운다. 현재 견적서는 명시적인 `선택 옵션 이미지 저장` 전까지 바뀌지 않는다. 다른 수동 HTML·ALT·공통/다른 옵션은 유지한다. 그다음 현재 대상의 UUID·슬롯으로 기존 편집/번역을 연결한다.
- 중복 위치나 현재 양식 개수 제한을 넘는 입력도 사진을 빠뜨리지 않고 초안으로 보여준다. 기존 저장 검증은 그대로여서 사용자가 초안을 정리한 뒤 저장해야 한다. 중복 위치의 ↑↓와 삭제는 정확한 index를 사용한다. 늦은 응답·활성 단계/버전/잠금 ABA·미저장 입력·저장 결과 미확인 상태는 초안 채택을 막는다.
