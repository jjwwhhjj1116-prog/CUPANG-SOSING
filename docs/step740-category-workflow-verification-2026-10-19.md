# Step740 — 카테고리에서 견적 자료까지 재검수

2026-10-19 KST. 기준 commit `999b05b30979d369fd12274a75f9a52a345965d3`, 운영 Worker `ce37f0d9-6b92-4073-a989-378c677f70d1`. 이 작업은 새 수집·접수 기능의 완성이나 새 운영 배포가 아니다. 앱·DB 모듈·확장의 runtime 변경은 없다.

## 확인한 범위

REA의 기존 보관 원본을 재사용해 필수 scalar, named array, 회사 기본설정, 초기 법적 고시, SEO 저장과 7단계 직접값·공란의 우선순위를 대조했다. 이 한정 범위에서는 새 구현 결함이 확인되지 않았다. 원본 함수 범위·SHA, Evidence와 별도 순수 검수의 한계는 [독립 감사](step740-category-audit.md)에 있다. 전 카테고리를 실제로 관측했다는 뜻은 아니다.

실제 기존 Chrome4의 앱에서 Supplier Hub 카테고리가 응답했다. `스포츠/레져 → 헬스/요가 → 헬스기구/용품`의 최종 목록에 `헬스보호대 81452`가 표시됐다. 이 경로는 1688 주소 접근이나 상품 수집을 실행하지 않는다. 실제 카테고리 조회 성공을 새 상품의 원문 수집이나 Hub 견적 접수와 혼동하지 않는다.

## 회귀검사 보정

최초 동결 실행은 16개 파일 **147건 중 140통과·7실패**였다. 실행 전후 앱·DB·확장·스크립트·시험 1,370개 SHA는 같았다. `outputs/step740-related-baseline-{freeze,proof}.json`과 로그를 보존한다.

실패를 앱에 맞춰 숨기지 않고 각각의 기존 계약을 확인했다.

- 카테고리 속성 규칙 2건: 기존 양식을 제자리에서 바꾸는 PUT200 기대는 현재의 형식 보호와 달랐다. PUT409와 별도 POST201을 함께 검사하고 원래 profile 전체 row, 1,000자 규칙과 수동 공란의 불변을 확인한다.
- 같은 파일 2건: 번역 fixture는 원문 `否`를 `아니요`로 번역한다. 원문 보존과 6개 옵션·최종 출력의 번역값을 각각 검사한다.
- 고시 fingerprint 3건: legacy 예상값 helper도 표시 전용 등록번호를 제외하도록 맞췄다. 별도 초기 고시 snapshot 이전 상품을 다루는 fixture에서는 그 marker가 없는 과거 자료를 명시적으로 구성했다. 새 수집의 독립 N/A 기본값 검사는 `initial-legal-notices`와 `intake-initial-legal-notices`에 계속 포함한다. 실제 notice binding 보정만 비교하며 상품 내용·자료 시계를 제외하지 않는다.

두 검사 파일의 중간 보정에서 신규 marker가 없는 대조군에도 marker 존재를 단언한 fixture 오류를 발견했다. 해당 실패 로그도 남겼고, 실제 고시 유무에 따라 단언하도록 고쳤다. 영향받은 13건과 최종 147건은 중복 합산하지 않는다. 독립 검토는 assertion 약화나 runtime 변경을 발견하지 못했다.

최종 같은 16개 파일의 동결 실행은 **147/147 통과**, 실패·취소·skip·todo 0이다. source SHA 1,370개가 실행 전후 같았다. 범위는 카테고리 선택, 보관 원문, 자체 API/SQLite/R2, 초기 고시, 직접 수정과 최종 whole-product 전송 자료의 구성까지다. 외부 원문 HTTP·번역·이미지·일부 양식은 격리 fixture이며 실제 접수가 아니다. `outputs/step740-related-release-{freeze,proof}.json`에 결과를 기록한다. 변경 시험 lint와 `git diff --check`도 통과했다.

## 실제 대기열에서 발생한 검수 실수와 복구

기존 입력 행의 카테고리 선택창에서 leaf 클릭을 조회 선택으로 잘못 취급했다. 현재 구현은 leaf 클릭이 즉시 확인 절차를 실행하는 구조다. 그 결과 첫 입력 행의 원래 `69900 / v1 / 개별 양식` 연결이 일시적으로 다른 저장 양식으로 바뀌고 자동 저장됐다. 이후 일반 UI로 코드69900을 다시 선택했을 때는 같은 경로의 유앤채 v2 Excel이 선택되어, 이것만으로 정확한 복구라 보고하지 않았다.

원래의 profile은 같은 owner에 보존된 ID `b21a1d06-7535-4818-970c-9f46355a8498`, revision1, template:null이었다. 과거에 보관된 와이홉 양식이라는 회사정보까지 임의로 바꾸지 않았다. 새 수집에서 회사 검사를 해제한 것도 아니다. 검수 전 화면의 코드·버전·개별 양식과 이 보관 profile을 대조했다.

복구는 해당 관리자 대기열 **첫 행의 profile만** 원래 서버 소유 v1 값으로 되돌리는 1,217byte SQL로 수행했다. owner·revision22·저장시각·정확한 행 ID·현재 profile ID·원래 profile revision/시각을 비교했다. 다른 행이나 상품을 쓰는 SQL은 없었다. 원래 양식·현재 대기열의 읽기 결과와 복구 전 상태를 ignored outputs에 보관했다. 최초 413KB 계획 SQL은 실행하지 않았고, D1 문장 한도 내의 bounded SQL만 실행했다.

별도 읽기에서 revision23과 기대 payload의 구조적 전체 일치, 두 번째 행·URL·특징·키워드 불변을 확인했다. 기존 상품의 ID·변경시각·견적 상태·Hub 상태·이미지 목록도 복구 전후 같았다. 화면에서 서버 초안을 다시 불러온 뒤 `69900 / v1 / 개별 견적 양식 연결` 및 `1~7단계 확인·수정` 버튼이 돌아온 것을 확인했다. 복구로 대기열의 저장 revision/시각은 증가했으므로 운영 쓰기 전체가0이라고 기록하지 않는다.

복구 증거는 `outputs/step740-intake-restore-proof.json`, 화면은 `outputs/step740-restored-intake.png`다. 기존 작업 상품·회사 기본설정·Hub/Couplus 견적서의 수정·재수집·전송은 없었다. 이 실수를 새로운 앱 결함이나 새 기능 개선으로 집계하지 않는다. 추가 카테고리 선택 검수는 기존 입력 행을 대상으로 반복하지 않는다.

## 남은 완료 조건

실제 신규1688 상품의 전체 옵션·원가·이미지 수집과, 수정 후 Hub 신규 견적서 접수번호 및 qvt/SKU 연결은 여전히 미검증이다. 이전1688/Open1688 site-safety 거절을 재시도하거나 다른 프로그램·확장·서버로 우회하지 않았다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`, `PRODUCT_DOCUMENT_LIVE_VERIFIED=false`를 유지한다. 완성률·전 카테고리 동일성·실접수 완료를 이 검사로 주장하지 않는다.

runtime가 바뀌지 않아 Worker와 확장0.2.86은 재배포하지 않는다. 실제 설치 확장 버전을 새로 확인했다는 주장이나 확장 새로고침 요청도 없다. 변경한 두 시험과 검수 문서만 Git에 반영한다.
