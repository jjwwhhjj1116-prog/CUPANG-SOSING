# 현재 페이지 수집 버튼 → YOOFAM 수집함 → 기존 초안 작성

## 반영한 동작

- RS 1.0.88 공개 배포물의 수동 수집·저장 확인 구조를 REA로 분석한 뒤 독립 코드를 작성했다. 근거와 한계는 `step747-rs-acquisition-audit.md`에 있다. 타사 코드를 실행하거나 패키지에 포함하지 않았다.
- 확장 0.2.89는 `detail.1688.com/offer/*.html*`의 최상위 문서에 **YOOFAM 상품 수집** 버튼을 표시한다. 직접 클릭한 이벤트에만 반응한다.
- 문서에 이미 있는 JSON·DOM에서 상품명, 옵션별 가격·이름·실제 SKU ID, 갤러리와 로드된 상세 이미지를 읽는다. JS 평가, 쿠키 읽기, 새 상품 요청, 상세 URL 요청, 타사 수집 서버 호출은 없다.
- 보이지 않은 SKU ID, 통화, MOQ는 `null`로 남는다. 표시용 옵션 키를 SKU ID로 만들지 않는다. 모호한 SKU 원문, 다른 상품 번호, 200개 초과 옵션, 외부 CDN 주소는 거절한다.
- 동일 Chrome 창의 앱에서 승인된 회원·회사 정보를 확인한다. 서로 다른 앱 계정이 같은 창에 있으면 전달하지 않는다.
- 회원·회사·앱 출처·창에 연결된 별도 확장 IndexedDB에 먼저 보관한다. 앱의 `/api/source-inbox` 저장 ACK와 회원·회사의 재확인 후에만 확장 보관본을 지운다. 응답이 불확실하면 보관본을 유지한다.
- D1 `source_inbox`는 회원별·상품번호별 최초 원문을 보존한다. 재수집은 명시적 중복 ACK로 처리하며, 기존 원문·검토본을 덮어쓰지 않는다. 수집함 제외는 원문을 보존하는 보관 처리이고 재수집하면 복원한다.
- 상품정보 검토본은 최초 원문과 분리하며 버전 조건을 검사한다. 확인한 옵션만 사용하고 필수 사실이 충족돼야 기존 초안 작성으로 넘어간다.
- 앱 수집함에서 카테고리를 직접 선택하면 새 대기열 행에 URL을 추가한다. 기존 작업 URL·대기열 URL의 중복 추가는 막으며, 기존 상품을 자동으로 수정·삭제하지 않는다.
- 기존 intake는 회원이 저장한 원문 ID·확인값·버전을 먼저 사용한다. 서버에서 소유자·회사·URL을 다시 확인해 기존 수집 영수증, 옵션·가격, SEO, 이미지 배치, 1~7단계 편집에 연결한다. 이 경로는 1688을 재요청하지 않는다.
- 새 수집함 조회가 불확실하거나 검토가 필요하면 새 원문 조회로 넘어가지 않는다. 이미 저장한 페이지 원문은 초안 작성 도중 재수집·상세 보완을 자동 실행하지 않는다.

## 확인

- 관련 최종 검사 **99개 통과**. 실제 함수·핸들러와 메모리 SQLite를 사용했다. 실제 1688·Supplier Hub에 합성 상품을 보내지 않았다.
- 실제 생성된 버튼 JS의 trusted click 검사, ACK 유실과 재개, 회사 변경, 회원 혼선, 서버 중복 저장, 검토 CAS, 보관·복원, 사용자 화면 종료 뒤 늦은 응답을 검사했다.
- 저장된 페이지 원문 → 별도 상품 초안 → 옵션 원가·실제 SKU → 선택 카테고리 견적 필드 연결을 검사했다. 별도 기존 상품·편집본이 동일하게 유지됐고, 이 경로의 1688 네트워크 요청은 0이었다.
- 기존 모바일 수집의 두 회사, 견적서 필수 입력 검토, XLSX 준비·전송 메시지 계약 회귀 검사를 통과했다. 합성 전송 메시지는 실제 접수 증거가 아니다.
- 타입 검사, 변경 코드 lint, 확장 생성물 검사, 운영 빌드 통과. D1 스키마 45개 테이블·17개 인덱스 일치.
- 새 버튼 생성물 검사도 운영 빌드의 선행 검사에 포함했다.
