# Step675 — 대표이미지 확대와 수정한 상세 HTML의 이미지 전달

기준은 Step674 `d7c46577e028e21a971b16b54d44b27ff558659a`다. 이번에는 3단계 대표이미지 확인 동작과 7단계에서 직접 수정한 상세 HTML을 견적서 파일로 전달하는 경로를 수정했다. 기존 쿠플러스·Supplier Hub 작업 상품과 운영 저장값은 변경하지 않았다.

## 대표이미지의 확인된 원본 동작

보관된 쿠플러스 UI artifact SHA-256 `ce8f14422c4e93a11592d886a369d633066a8a9f4cdba9f37dbb1276d798c6cc`에서 현재 대표이미지 클릭 → 전체 화면 표시, 배경·이미지·닫기 버튼 클릭 또는 Escape → 닫기를 확인했다. 열기와 닫기는 `fullscreenPreview`만 바꾸며 선택 이미지나 견적서를 저장하지 않는다. 현재 이미지 URI를 그대로 표시한다.

REA parent Evidence는 `ev_f212771bf00c7a08d98f8a961c3c8d31f59ace3877c40d19fbb9a13334646111`, summary는 `ev_04caff46eefc087f8725beaf7b7fd4c0997c567b7bd4ff5a1e6bdb0f6ad54c23`다. opener UTF-16 `[61729,61803)`, Escape `[62832,62919)`, 클릭 영역 `[33796,34029)`, overlay `[36080,36483)`를 포함한 8개 조각·2,904 bytes를 분석했으며 구문 분석 실패는 없다. ignored `outputs/step675-image-audit/`에 범위·digest·근거를 보관했다. 이는 정적 클라이언트 근거이며 비공개 서버 동작이나 전체 화면의 픽셀 일치를 입증하지 않는다. 추가이미지의 자동 carousel은 확인되지 않아 새로 구현하지 않았다.

`ImageFullscreenPreview`와 현재 대표이미지 버튼을 연결했다. 인증된 기존 이미지 URL을 그대로 사용하며 JS 저장·업로드·별도 이미지 수집을 하지 않는다. 이미지 렌더링에 필요한 브라우저 GET만 발생한다. 닫기, Tab 순환과 포커스 복원은 확대 창 안에서 처리하며 Escape가 상위 작업 창까지 닫지 않게 한다. 상품·프로필·저장 버전·옵션·선택 이미지·소유 풀·단계 변경은 이전 미리보기 상태를 무효화한다.

번역 OFF에서도 읽기 전용 확대가 가능하다. 기존 부모가 이 prop을 단계 표시 구분으로도 사용하므로 `translationEnabled`는 이전 확대 상태를 무효화하는 기준에 포함하고, 확대 가능 조건에는 사용하지 않는다. 검토 중 발견한 대표이미지 → 가격 → 대표이미지 복귀 시 이전 확대가 자동으로 다시 나타나는 문제를 수정하고 회귀 검사를 추가했다. 실제 owner 전환은 기존 부모의 상품 소유자 확인·unmount 및 파일 인증 경계를 그대로 사용한다.

## 직접 수정한 HTML의 이미지 누락 수정

기존 `resolvePublicDetail`은 수동 HTML 행을 전부 건너뛰었다. 자동 생성된 HTML을 복사해 문구를 수정한 뒤 저장하면 자체 `/media/quotation/…` 주소는 견적서에 남지만, 첫 파일 생성에 필요한 이미지 게시 목록은 비어 있을 수 있었다. 그 결과 견적서 안의 이미지 주소가 404가 될 수 있었다.

수동 HTML을 parse5로 실행 없이 읽어 실제 `img src`만 확인한다. 원문 HTML·문구·속성·공란은 다시 작성하거나 정규화하지 않는다. 외부 주소를 가져오지 않는다. 현재 행의 상세 이미지 역할 목록, 현재 상품의 소유 이미지 풀, 현재 owner·서명 설정으로 확인되는 자체 주소만 게시 목록에 포함한다. 제외 행만 참조하는 이미지와 중복 주소는 새 게시 대상을 늘리지 않는다. 기존 견적서 첨부 조회가 같은 역할 목록을 사용하므로 API route 변경은 필요하지 않았다.

현재 자체 주소의 잘못된 토큰·삭제된 이미지·다른 상품 참조와, 현재 선택 이미지 토큰으로 확인되지만 origin이 달라진 주소는 원문을 유지하고 검토 오류를 표시한다. 엔티티로 표현한 주소, scheme-relative 및 브라우저에서 동등한 대문자 scheme·호스트·기본 포트는 같은 이미지로 확인한다. 호스트가 없는 상대 경로는 Supplier Hub에서 다른 호스트로 해석될 수 있어 오류로 남긴다. GIF 검토도 같은 파싱 결과를 사용하므로 엔티티 표현으로 검토 오류가 빠지지 않는다. script·style·template 등 비활성 영역의 문자열은 게시를 허용하는 근거가 아니다.

기존 일반 외부 이미지 주소와 공개 이미지 설정이 없는 경우의 계약은 유지한다. 설정이 없어 과거 origin·서명을 확인할 수 없는 주소를 임의로 자체 주소로 분류하지 않는다. 실제 공개 호스트의 DNS·Access·외부 접근 가능 여부를 검증했다는 뜻도 아니다. 읽기·미리보기에는 게시가 없으며, 사용자가 파일 생성·패키지 내보내기를 요청할 때만 기존의 조건부·불변 파일 복사 방식을 사용한다.

## 검수

수동 HTML의 공통·옵션 값, 공란·외부 주소, 중복·혼합·제외 참조, 토큰·origin·이미지 선택 변경, 엔티티·scheme-relative 주소, GIF 검토와 실제 API/SQLite 견적 파일을 검사했다. 두 회사의 실제 handler 검사에서 수정한 HTML은 CSV·견적 필드에 그대로 남았고 이미지 응답은 파일 생성 전 404, 생성 후 200이었다. 파일 생성 전후 DB 스냅샷이 같고 공개 호스트·1688·Supplier Hub에 외부 요청은 없었다. 기존 submission-review mock에는 원래 소스가 이미 사용하는 `useLayoutEffect`를 추가했으며 기존 검증 단언은 유지했다. 초기 mock 실패를 수정 후 통과 개수에 중복 합산하지 않는다.

대표이미지 신규 검사는 두 회사의 번역 OFF 확대, 모든 닫기 경로, 포커스, 실제 이미지·견적서 저장 불변, 이전 콜백과 단계 왕복을 포함한다. 최종 관련 **7파일 118개**가 통과했다(상세·견적서 88개, 대표이미지 30개; 서로 중복 없음). 마지막 단계 왕복 수정 후 기존 대표이미지 편집기 9개도 재확인했으며 이를 새 통과 개수로 다시 더하지 않았다. 최종 타입 검사·변경 파일 lint와 Worker 빌드가 통과했고 독립 검토의 미해결 지적은 없다. 검사 기록은 ignored `outputs/step675-export-checks.json`, `step675-main-fullscreen-preview-final-tests.log`, `step675-main-editor-final-regression.log`, `step675-final-types.log`, `step675-build.log`에 보관했다.

지정한 동일 Chrome3에서도 실제 대표이미지 편집기·견적서 API, 임시 SQLite·이미지 저장소를 사용했다. 두 회사의 선택 이미지 URL과 확대 URL이 같고 포커스·Tab·Escape·닫기 버튼·이미지 클릭이 작동했다. CSS 전체 화면의 경계는 사용 중인 소수 배율에서 정수 viewport와 1 CSS pixel 미만 차이였다. 확대는 견적서 쓰기를 만들지 않았다.

두 회사 각각 원래 자동 HTML의 문구를 직접 수정해 저장 → 견적 미리보기 → 파일 생성 → 실제 공개 이미지 handler 조회를 진행했다. 미리보기 후에도 404·게시 0, 파일 생성 후 PNG 200·게시 2개를 확인했고, 읽어온 HTML과 CSV의 인용 처리된 HTML 셀을 원문과 대조했다. 총 HTTP 37회 중 수동 PUT 2회·미리보기 POST 2회·파일 생성 POST 2회가 모두 성공했다. 임시 이미지 4개, 실제 외부 요청·운영 DB 쓰기 0, 최종 sourceFrozen=true다. 공개 주소는 합성 HTTPS origin이며 조회는 로컬 proxy에서 실제 handler를 호출한 것이므로 운영 공개 호스트 접속 증거로 사용하지 않는다. 이미지 GET과 인증·카테고리·저장소는 명시한 fixture 경계다. PNG 촬영은 timeout으로 실패해 이번 screenshot 성공 파일은 없다. 근거는 ignored `outputs/step675-native-{dom-proof,proof,verification}.json`과 재현 스크립트에 보관했다.

## 운영 반영과 남은 작업

자체 탭과 loopback 3665 검수 서버는 종료했다. 새 migration·확장 업데이트·유료 자원·새 OAuth 요청은 없다. 원격 `0024_product_registration.sql` 적용 및 Step669 이후 운영 배포는 Cloudflare 인증 확인 대기이며, 마지막 확인 운영 Worker는 Step668 `c9f47c1e-9d46-49c7-8eb4-fef0f70d8021`이다.

전체 완료에는 새 1688 상품의 전체 SKU·이미지, 모든 카테고리의 실제 공식 양식·기본값, 나머지 단계 기능과 Supplier Hub 동의·최종 접수 번호·SKU 대조가 남아 있다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`와 운영 mutation gate=false를 유지한다. 이번 부분 검수를 전체 동일구현 또는 실제 등록 접수 완료로 보고하지 않는다.
