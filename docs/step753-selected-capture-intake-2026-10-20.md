# 재수집본 선택부터 초안 편집까지 연결

기준 커밋은 `8936c54`이다. 이번 변경은 수집 원문 보관과 선택한 수집본의 전달, SEO 검색태그 편집을 다룬다. 기존 실상품을 열거나 수정하거나 전송하지 않았다.

## 수정한 동작

기존 수집함은 회원·1688 상품 번호가 같으면 처음 저장한 자료만 유지했다. 이후 수집한 자료에 새 SKU·가격·속성·이미지가 있어도 새 요청의 성공 응답과 실제 저장 원문이 달라질 수 있었다. 원래 `source_inbox` 행을 보존하고 `source_inbox_captures`에 재수집 버전을 추가하도록 변경했다. 같은 fingerprint의 재전송은 중복 보관하지 않는다. 각 버전의 검토값·제외 상태·revision은 독립적이다.

수집함에서 고른 정확한 ID·fingerprint·검토 revision·canonical URL을 카테고리 선택, 대기열 임시저장·복원, 초안 요청까지 유지한다. 카테고리·특징·키워드 수정은 선택을 유지하고, 다른 상품 URL로 바꾸면 해제한다. 최신 수집본이라는 이유로 다른 버전으로 교체하지 않는다. 서버가 확인한 원문과 ACK, import 직전 다시 읽은 원문도 비교한다. 불확실한 ACK를 다른 저장 결과의 GET 응답으로 성공 처리하지 않는다.

원본 저장은 활성 40개·보존 200개 한도를 원자적 SQL로 확인한다. 한도 초과 시 기존 자료를 삭제하지 않고 명시적으로 거절한다. 이 한도는 전체 상품 목록의 한도가 아니다. 기존 보존 원문을 자동 정리하는 기능은 이번 범위에 없다.

SEO의 일반 공란 입력 정책은 유지하면서, 사용자가 명시적으로 ‘검색태그·견적서 태그 함께 비우기’를 선택하면 `keywords:[]`를 저장하도록 연결했다. 견적서에서 직접 수정한 공통·옵션 태그는 유지한다. 수동 상품명·옵션명과 다른 미저장 편집은 이 동작으로 사라지지 않는다.

선택한 수집본의 이미지 반영이 일부 실패한 경우 같은 수신 원문을 서버에서 다시 확인한 뒤 누락된 원본만 재개한다. 이미 반영된 상품의 SEO·이미지 역할 편집을 재실행하지 않는다. 두 창이 동시에 상품화하는 경우에도 DB의 실제 생성 여부를 ACK에 전달해 먼저 생성된 기존 작업의 편집을 보존한다.

## 검증 근거

- `outputs/step753-browser-qa/proof.json`: 실제 React 수집함 → 카테고리 선택 → 실제 로컬 API·SQLite → SEO·원본 이미지 초안 → 수동 SEO 저장. 합성 수집본 2의 원가 7 CNY·1옵션을 반영했고, 기존 합성 상품·수신 원문과 첫 수집본의 SHA가 변하지 않았다. 외부 1688·Supplier Hub 요청은 0이다. AI 응답·상품·분류·이미지는 격리 fixture이므로 실상품 수집 성공 증거가 아니다.
- `outputs/step753-browser-qa/seo-saved.png`: 수동 수정과 견적서 자동 태그 공란 저장 화면.
- `outputs/step753-source-inbox-deploy-audit.json`: 기존 행이 있는 migration 반복 적용, 복합 FK, 활성·보존 한도와 동시 lazy DDL 검수.
- `outputs/step753-related-final-proof.json`: 최종 단일 실행의 고유 시험 파일·통과 수와 실행 전후 소스 해시. 집중·반복 검사는 합산하지 않는다.
- `outputs/step753-installed-extension.ax.txt`: 동일 Chrome에서 설치 버전 2.1.4를 직접 확인. 이번 배포의 확장 소스·권한·ZIP은 변경하지 않는다.

## REA 및 실제 전송의 남은 범위

REA 원본 증거는 기존 보관된 Couplus·Supplier Hub 배포 코드를 재사용했다. `outputs/step753-native-legal-contract.json`에 정확한 파일 SHA·선택 범위와 기존 Evidence ID를 남겼다. 인증·MSDS 등 native 첨부는 문서 ID별 fileType 전송이며, 인증 파일명의 행 번호는 schema 정렬 기준이다. 이를 옵션 번호로 추정해 전송하지 않았다. 현재 원격 wire·첨부 수용·binary readback·최종 접수는 관측하지 않았다.

기존 Chrome의 별도 검수 탭에서 Supplier Hub 유앤채 회사 표시와 빈 신규 등록 시작 화면을 읽기만 확인했다. 기존 견적서를 열지 않았고 동의·업로드·다음 단계·제출은 실행하지 않았다. 실제 등록 접수와 동일한 검증으로 확대 해석하지 않는다.

1688의 이전 자동 승인 검토 거절 대상은 다른 도구·확장·서버·CLI를 통한 재접근도 하지 않았다. 따라서 이번 작업으로 새 1688 실상품 수집 → 전체 단계 → Supplier Hub 최종 접수가 검증됐다고 보고하지 않는다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`, `PRODUCT_DOCUMENT_LIVE_VERIFIED=false`를 유지하며 임의 완료율을 제시하지 않는다.

## 운영 반영

새 테이블만 기존 D1에 추가했다. 기존 행을 바꾸는 migration은 없다. `--file` 가져오기 요청의 인증 오류 뒤 동일 CREATE TABLE을 D1 query API로 실행하여 성공하고 스키마를 다시 읽어 확인했다. 실패 로그와 최종 성공 로그를 모두 보관했다. 새 유료 리소스·provider·계정 권한은 추가하지 않았다.

최종 25개 고유 시험 파일의 429개 검사가 전부 통과했다. 실패·취소·skip은 0이며, 입력 1,457개 파일의 검사 전후 SHA가 같다. 첫 요약기가 Node 기본 spec reporter의 기호를 TAP로만 해석한 문제는 로그 재해석으로 바로잡았으며, 시험 자체의 exit는 처음부터 0이었다. 반복 실행을 합산하지 않았다. 타입·린트·46테이블/17인덱스/30모듈 스키마 검사·최종 운영 빌드가 통과했다.

기존 Worker에 `568427e9-72ac-496e-91b3-94c04ff24826`을 배포했다. 동일 Chrome에서 admin 로그인과 기존 목록 2행·대기열 1건·기존 수집본 1건 조회를 확인했다. 새 버전 표시가 있는 운영 수집함을 읽고 닫았으며 상품 열기·수집 시작·편집·제출은 0이다. 화면 증거는 `outputs/step753-production-inbox.ax.txt`와 `.png`다. 확장 2.1.4의 84파일 ZIP SHA는 `d6daf948ea2c85507bbf3a5fd8bc5261245f1bd1eeb29e7d0b319b9386eabe8b`로 변경되지 않았다.

ACK 이후 다른 창의 명시적 source-supplement와 상품 import를 하나의 트랜잭션으로 잠그는 전체 경계는 이번 범위에 포함하지 않았다. import 직전 원문 비교를 보강했지만 전체 경합을 모두 검증했다고 주장하지 않는다. 최종 소스 검토는 `outputs/step753-source-review.json`, 배포·검사·SHA 종합 검증은 `outputs/step753-final-validation.json`이다.
