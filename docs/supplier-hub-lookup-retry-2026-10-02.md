# Supplier Hub 전송 후 결과 응답 유실 처리

## 변경 이유

등록전송과 검증 재개는 이미 파일 검증 결과에서 견적서 ID를 얻고, 그 ID로 옵션별 SKU 결과를 자동 조회한다. 그러나 앱과 확장 사이의 결과 응답이 한 번 시간초과되면 이 조회가 즉시 종료됐다. 사용자는 이미 올린 파일의 결과를 다시 직접 확인해야 했다.

## 처리 범위

- `RESULT`, `REFRESH`, `REGISTRATION`의 **로컬 응답 타이머**만 `SupplierHubLookupUnavailable`로 구분한다. 확장이 명시적으로 반환한 오류, 잘못된 응답, 회사·양식·저장본 불일치, 취소는 이 오류로 바꾸지 않는다.
- 자동 결과 추적은 응답 유실에 한해 3초, 10초, 30초 뒤 다시 조회한다. 연속 네 번째 실패에는 종료한다. 정상 응답을 받으면 연속 실패 횟수를 초기화한다.
- 최대 2시간/300회의 기존 조회 한도를 유지한다. 남은 시간보다 오래 기다리지 않으며 기다리는 중 취소할 수 있다.
- 시간초과 직후와 다음 조회 직전, 응답을 적용하기 전에 현재 승인 회사·상품·카테고리·선택 양식·저장 지문을 대조한다. 저장값이 바뀌면 오래된 견적서 조회를 이어가지 않는다.
- 검증이 끝난 견적서의 ID는 다음 SKU 조회의 기준으로 유지한다. 복원한 과거 SKU 행을 새로운 관측으로 취급하지 않는다.
- 응답 유실은 접수·거절 증거가 아니다. 마지막 확인 결과는 유지하고 새 결과/접수 기록으로 발행하지 않는다. 앱에는 현재 다시 확인할 대상과 대기 시간을 표시한다.
- 재조회 경로에는 ZIP 출력, 첨부, 등록전송, 검증 클릭이 없다. 쓰기 요청의 응답 유실을 자동 재실행하지 않는다. 확장 자체의 조회 중 잠금 오류 등 명시적인 오류도 자동 반복하지 않는다.

## 검증

실제 앱 컴포넌트·브리지·추적 함수로 응답 유실→재조회→SKU 표시를 검사한다. 두 허용 회사 `A01464742`(와이홉), `A01526306`(유앤채)에서 파일 출력과 등록전송은 각각 한 번이다. 브리지 타이머/리스너 해제와 이전 요청의 늦은 응답 거절을 확인한다. 반복 실패 한도, 성공 후 실패 횟수 초기화, 시간 한도, 취소, 중간 저장본 변경, 오류 콜백도 포함한다.

집중 검사 76/76, 전체 검사 1,827/1,827(284.641초), TypeScript 및 변경 파일 린트 오류·경고 0, 운영 빌드·11개 마이그레이션 확인·확장 원본/ZIP 일치 검사를 통과했다. 운영 배포 결과는 이번 `HANDOFF.md` 555 항목에 기록한다. Hub 응답과 SKU는 테스트 fixture이며 실제 운영 접수번호가 아니다.

## 적용

앱을 새로고침하면 적용된다. 확장은 기존 0.2.39를 유지하며 이번 변경에 재설치가 필요하지 않다. DB 구조·회사 허용 목록·원래 가격 계산과 1~7단계 작성값을 변경하지 않는다.

실제 승인 계정에서 전 카테고리 Couplus 기본값 대조, 운영 AI/이미지 번역, 추가 필수 서류와 두 회사의 최종 Hub 접수번호/SKU 확인은 별도 미완료 항목이다. 이번 합성 검사나 기존 공개 1688 수집 결과만으로 완전 복제를 판정하지 않는다.
