# 상품추가 카테고리·URL 임시저장 응답 유실 복구

## 재현된 문제

상품추가 대기열은 서버의 현재 버전으로 임시저장한다. 서버 저장 뒤 HTTP 응답만 유실되면 앱은 버전을 갱신하지 못했다. 이후 ‘저장 다시 시도’도 이전 버전으로 PUT하므로 실제 저장 API는 계속 409를 반환한다. 서버 초안을 불러오면 그 사이에 수정한 URL·특징·키워드를 교체해야 하는 상황이었다. 또한 HTTP 200과 `draft` 존재만으로 저장 성공을 처리해, 다른 입력을 돌려준 응답도 미저장 상태를 지울 수 있었다. 수정 전 신규 회귀 두 건에서 복구 GET이 없는 것과 다른 목표의 응답으로 dirty가 해제되는 것을 확인했다.

## 구현

- 임시저장 응답의 버전·행·목표·시각을 검사한다. 저장 확인은 요청의 다음 버전과 모든 행의 ID·카테고리 설정 ID/버전·URL·특징·키워드·순서·목표가 일치해야 한다. 서버가 관리하는 카테고리 설정을 클라이언트 메타데이터로 대체하지 않는다.
- 확인되지 않은 마지막 저장 요청과 입력 변경 세대를 hook ref에 보존한다. 실패한 PUT 뒤 현재 계정의 GET을 조회해 정확히 같은 입력이 저장됐는지 확인한다. 원래 저장 버전이 그대로면 미저장 상태와 오류를 유지한다. 다른 입력이나 더 먼 버전이면 자동으로 덮어쓰거나 저장 완료로 처리하지 않는다.
- 복구 GET도 실패하면 마지막 요청을 유지한다. 사용자가 다시 저장할 때 먼저 원래 요청을 조회한다. 이미 저장됐고 새로운 수정이 없으면 추가 PUT 없이 복구한다. 새 URL·키워드가 있으면 복구한 다음 버전으로 그 수정분을 저장한다.
- 저장 중 새로 입력한 내용을 서버의 이전 응답으로 교체하지 않는다. 미저장 상태를 유지하고 최신 변경을 이어서 저장한다. 실제 다른 창의 변경은 입력을 유지한 채 일시중지하며, 기존 ‘서버 초안으로 교체’의 확인 절차를 따른다.
- 화면 해제 시 저장/복구 조회를 함께 취소하고 늦은 응답을 반영하지 않는다. 새 UI 단계·추가 전송 동작·DB 변경·확장 변경은 없다.

## 검증 범위

집중 15/15: 저장 중 입력 변경, 저장 응답/복구 조회의 연속 유실, 다음 버전 저장, 추가 PUT 없는 복구, 실제 다른 창 충돌, 저장되지 않은 503 뒤 재시도, 잘못된 HTTP 200/서버 초안, 취소 후 늦은 응답, 카테고리/버전/입력 불일치 거절을 검사했다.

와이홉 A01464742·유앤채 A01526306 각각 실제 임시저장 API와 임시 SQLite에서 저장 응답과 첫 조회 응답을 유실시켰다. 이후 수정한 지정 URL의 쿼리와 키워드가 버전 2로 저장됐고, 원래 선택한 80719 설정 연결과 단일 초안 레코드가 유지됐다. 인증과 카테고리 조회는 fixture이며 80719는 관찰한 폼 계약 시험이다. 이 시험이 선글라스의 실제 판매 분류나 Supplier Hub 등록을 검증한 것은 아니다. 실제 계정 상품 및 Hub에 쓰지 않았다.
