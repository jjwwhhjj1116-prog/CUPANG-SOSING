# 공식 필수 항목·계정별 대기열·표시사항 재생성 연결 — 619

기준 커밋은 `a03464976c597562ae9a3b40da683253aeab9423`다. 카테고리 선택 → 1688 URL 적용 → 수정 가능한 1~7단계 → 사용자 확인·수정 → 명시적 Supplier Hub 전송 → 접수·SKU 확인 흐름에서 실제 재현된 세 가지 오류를 수정했다. 기존 운영 상품·대기열·가격·기본설정은 개발 검수 중 수정하지 않았다. 확장 프로그램과 DB 스키마도 변경하지 않았다.

## 공식 원본의 필수 항목

원본 XLSX의 6행에 ‘필수’라고 명시된 열을 Single 양식의 선택 입력 필드에 연결하고 저장된 열 연결의 `required` 체크를 끄면, 수동 공란이 필수 누락 보고에서 빠졌다. 원본 파일을 검증해도 이미 연결된 열이라는 이유로 원본 필수 표기가 다시 검사되지 않아 전송 준비의 `EXCEL_REQUIRED_MISSING` 오류가 사라지는 경로를 재현했다.

출력기는 원본 SHA-256·헤더·공식 입력 행 구성을 검증한 뒤, 정확한 ‘필수’ 표기가 있는 연결 열의 공란을 기존 필수 누락 결과에 합친다. 행·열로 중복을 제거한다. 공란을 임의 값으로 채우거나 저장된 열 연결 체크를 다시 쓰지 않는다. ‘선택’·‘조건부 필수’·일반 CSV/XLSX의 기존 의미는 유지한다.

양식 편집 화면도 읽은 원본의 정확한 ‘필수’ 열을 체크·비활성 상태와 ‘원본 필수’로 표시한다. 기존 저장 설정이 `required:false`여도 표시를 끌 수 없으며, 원본 조회만으로 저장 요청은 발생하지 않는다. 이 표시는 원본의 표기이고 새 회사·접수 증명으로 주장하지 않는다.

두 회사의 원본 OOXML·R2·profile API·상품 초안·수동 공란 fixture에서 미리보기의 필수 오류 6개와 ZIP 첨부 준비 거절을 확인했다. 사용자가 실제 값을 입력하면 오류가 없어지고 6옵션 패키지를 준비할 수 있다. 원본 안내·예시·수식·드롭다운·잔여 상품 보호, 조건부·선택·일반 양식, 중복 제거도 유지했다.

## 계정별 대기열 저장 범위

이전 계정에서 시작한 대기열 자동저장이 로그인 쿠키 변경 뒤 다른 계정으로 실행되면, 두 계정의 revision이 같을 때 새 계정의 초안을 덮어쓸 수 있었다. 특히 완료한 행을 제거한 빈 `rows` 요청은 카테고리 소유 검사도 거치지 않아 다른 회사의 URL 입력을 지울 수 있었다.

GET과 저장 응답은 인증된 owner를 반환한다. PUT은 화면에서 확인한 `expectedOwnerId`와 현재 인증 계정의 정확한 일치를 요구하며, 누락·불일치는 409로 거절한다. 예전 클라이언트 요청을 현재 계정으로 추정해 받아주는 fallback은 없다.

클라이언트의 초안 hook을 화면 계정에 묶었다. 계정 변경은 진행 요청을 취소하고, 요청 세대를 바꾸며, 이전 조회·저장·응답 유실 복구·타이머·입력 콜백을 무효화한다. owner가 없으면 조회도 시작하지 않는다. 같은 계정의 정상 자동저장·복구·수동 재시도와 URL·특징·키워드·작업 목표 보존은 유지한다.

두 회사에 동일한 revision 1의 초안을 저장한 실제 로컬 API/SQLite 회귀에서, 계정이 바뀐 완료 행 제거 요청은 양방향 모두 409이며 두 초안의 저장 바이트가 일치했다. 내용과 다음 revision이 우연히 같은 다른 계정의 응답도 저장 완료로 흡수하지 않는다. 원래 계정으로 돌아오면 이미 저장된 요청을 조회로 확인하고 중복 PUT을 만들지 않는다.

## 같은 범위의 제품 표시사항 재생성

6단계의 9행 표시사항에서 재질·제품명 등을 수정하고 PNG를 다시 생성·연결해도, 같은 옵션의 이전 생성 PNG와 새 PNG가 최종 라벨 참조에 모두 남았다. 이전 라벨의 계획이 오래됐다는 `GENERATED_PRODUCT_LABEL_STALE`가 계속 발생해 XLSX/ZIP 전송 준비를 막는 상황을 실제 API로 재현했다.

인증된 파일 조회에서 서버가 기록한 제품 9행 라벨 증명을 반환한다. 명시적 연결은 같은 상품·옵션·유효 profile·카테고리의 증명된 이전 제품 라벨 참조만 교체한다. 원본 이미지 풀과 R2 바이트, 수동·legacy 파일, 공통 범위, 다른 옵션·profile·카테고리와 7단계 고시 라벨은 보존한다. 파일명은 조회 위치로만 사용하며 교체 근거로 추정하지 않는다.

새 PNG도 정확한 파일 키·상품·옵션·profile·카테고리와 현재 9행 계획 SHA를 서버 증명과 대조한다. 최초 재사용 키, 정상 업로드 결과, 업로드 응답 유실 뒤 복구 키, 이미 전달된 `uploadedKey` 모두 이 검사를 거친다. 같은 업로드 번호에 증명 없는 수동 파일이 있어도 이전 증명된 라벨을 그 파일로 교체하지 않는다. GET 실패·다른 owner 응답·누락 또는 잘못된 증명은 풀·견적 참조 변경 전에 중단한다.

업로드 중 9행 수정, receipt 조회 중 견적 경합, 이미 연결된 무변경 경로도 현재 원천과 CAS를 다시 확인한다. 응답 유실 재시도는 기존 업로드·저장 결과를 먼저 읽고 중복 PNG·PUT을 만들지 않는다. 새 검사는 두 회사의 실제 API·R2·XLSX·ZIP에서 범위·원본 보존과 오류 해제를 확인했다. 기존 수동 참조 제외 회귀도 재생성 직후 stale 0 → 사용자의 수동 이전 라벨 재연결 뒤 stale 1 → 명시적 제외 뒤 stale 0을 확인하도록 유지했다. 라벨 계획의 증명은 모든 이미지 픽셀의 번역 정확도를 자동 증명하는 것은 아니다.
