## 원본에서 확인한 두 차이

REA로 확보한 기존 shipped artifact와 분석 기록을 재사용했다. vendor 코드를 실행하거나 새 원문 요청을 하지 않았다. 현재 main SHA-256은 `36a8e3252cba8096da3e9b06eaf3c338699dce35280a0080484a5c7181d20fb7`, 현재 route SHA-256은 `2fb15d370c331f65d982a886f2888b813ccae67277e87f806182c70032821664`다.

원본 main의 `updateProductWithCoupangDocPartial`는 SEO 옵션 저장 전에 `applyBundleSuffixToSeoOptions`를 적용한다. 후자는 직접 부모의 요청 이름을 우선해 현재 묶음 수량으로 자식 이름을 만든다. helper UTF-16 범위는 `[187402,188322)`, raw SHA는 `91d37d01e580d45c2ba8813e980550e2039af0060cb2ab1d572d5c9e1257d463`이다. 자체 저장은 변경한 UUID에만 이름을 반영해, 부모를 `검정`에서 `남색`으로 수정해도 자식의 예전 이름이 남았다. 별도 옵션 편집기의 응답 확인도 요청 UUID만 예상해, 서버가 올바르게 자식 이름을 바꾸면 저장 성공 응답을 거절할 수 있었다.

현재 route의 `saveManualLabels`는 입력 정보로 PNG를 생성·업로드하고 견적서의 `labelImages`도 함께 갱신한다. 범위 `[151173,153321)`, raw SHA `44c4e768b548e7c8e215de4eea359c1bea618cd4a1765923ceac9982be92c4ce`다. 자체 기본 저장은 텍스트만 저장하고 PNG 생성·견적서 연결을 별도 조작으로 요구했다. 이전 REA 단계별 분석은 [Step727](step727-rea-stage-contract-2026-10-19.md)을 참조한다.

## 반영한 동작

`option-seo-names.ts`는 명시적으로 실제 바뀐 부모 이름에 대해서만 저장된 직접 `bundleSources` 자식 연결을 따른다. 생성 당시 수량 대신 현재 `unitsPerPack`으로 접미사를 만들며, 1개로 해제된 묶음은 그대로 둔다. 부모가 함께 변경되면 같은 요청의 자식 이름보다 부모가 우선하는 원본 규칙을 적용한다. 원본은 공백을 trim하지 않으므로 truthy 공백도 같은 규칙을 따른다. 자식만 수정한 경우·부모 공란·부모 값이 실제로 바뀌지 않은 경우는 기존 직접 입력을 보존한다. 간접 자식을 임의로 연쇄 변경하지 않으며, 500자를 넘는 파생 이름은 전체 저장 전에 거절한다. 가격·포장·이미지·포함 여부·순서는 유지한다. 일반 조회나 이전 데이터 일괄 변경은 없다. 별도 옵션 편집기의 예상 응답에도 같은 규칙을 적용했다.

`ProductLabelEditor`의 **정보 저장하기**는 검토한 텍스트·구조의 저장, 같은 저장값의 PNG 생성, 업로드, 견적서 연결을 한 번의 명시적 동작으로 이어간다. 수정하지 않은 기본값도 이 버튼으로 연결할 수 있으며, 이때 빈 텍스트 PUT은 보내지 않는다. 저장 후 부모 화면 갱신은 PNG 연결 완료 또는 실패 확인 뒤에 수행해 중간에 작업이 취소되는 문제를 피한다.

새 `product-label-save.ts`는 생성 전후 최신 저장값을 비교하고 기존 업로드 영수증·파일 캐시·연결 검증을 재사용한다. 텍스트 저장 뒤 업로드나 연결이 실패하면 저장된 입력은 남기고 미완료 상태를 유지한다. 재시도는 같은 저장값·렌더 결과·이미 업로드한 파일을 재사용하며 완료하지 않은 이미지 연결을 성공으로 표시하지 않는다. 저장·업로드 응답 누락은 먼저 조회해서 확인한다. 기존 수동 미리보기/연결로 복구해도 정확한 연결 확인 뒤 미완료 상태를 해제한다. 실패 때문에 새 AI 초안을 자동 요청하지 않는다.

범위의 한계도 유지한다. 원본 표시사항 저장은 모든 옵션에 같은 이미지와 입력을 덮어쓰는 분기가 있지만, 이번 변경은 현재 선택 옵션 또는 상품 공통 범위의 저장을 연결한다. 다른 옵션의 독립 수정값을 몰래 덮어쓰는 동작을 추가하지 않았다. 이 변경만으로 표시사항 전체가 원본과 모든 경우 동일하다고 선언하지 않는다.

## 검사 범위와 실제 검증의 경계

묶음 이름 검사는 실제 SEO React callback→로컬 API/SQLite→견적 옵션명→화면 재열기, 양사 계정, 저장 응답 누락의 조회 복구와 전체 저장 거절을 포함한다. 표시사항의 새 통합 검사는 실제 버튼 callback·연결 helper·로컬 API/SQLite/R2와 견적 이미지 참조·파일 bytes를 검사한다. 이 통합 검사의 renderer는 고정 PNG를 반환하는 경계 fixture다. 실제 renderer의 항목·공란·유니코드·캔버스 크기·출력 제한은 별도 `product-label-render` 검사에서 확인한다. 실제 브라우저 픽셀 검수나 실제 상품 이미지의 완성도를 입증하는 시험으로 바꾸어 말하지 않는다.

독립 검토에서 저장 응답의 자식 옵션명 비교, 변경 없는 저장에서 빈 변경 검증, 부분 실패 후 수동 연결 완료 상태, 자동 초안 재요청 차단을 검토·수정했다. 회사 메뉴 닫힘과 견적서 버전 전달도 별도로 점검했으나 보관 근거에서 수정할 오류는 발견되지 않았다. 메뉴는 각 실행 전에 회사코드를 다시 확인하고, schema 버전은 native 저장 때 증가하는 필드로 관찰되지 않았다.

1688 두 주소는 Step732의 명시적 읽기 재승인 후에도 사이트 안전 정책으로 거절됐다. 이번에는 해당 주소를 재시도하거나 대체 도구·확장·원격 서버로 우회하지 않았다. 실제 새 상품 원문 수집·최종 native POST·접수 ID 확인은 아직 미검증이며, `SINGLE_DOCUMENT_LIVE_VERIFIED=false`와 `PRODUCT_DOCUMENT_LIVE_VERIFIED=false`는 유지한다. 원본의 private 수집 공급자·키·캐시를 확보했다는 주장도 하지 않는다.

세부 근거는 `outputs/step734-seo-bundle-name-proof.json`, `step734-label-runtime-freeze.json`, `step734-related-closure-{freeze,proof}.json`에 보관한다. 집중 검사와 통합 검사는 겹치므로 통과 수를 더하지 않는다.

동결한 SEO 변경의 집중 검사는 59/59, 표시사항의 마지막 동결 후 검사는 22/22 통과했다. 앞서 실행한 표시사항 37건은 최종 검사와 겹치며 합산하지 않는다. 두 변경은 독립 담당이 최종 SHA로 재검토했고 미해결 중요 발견은 없었다. 아래 견적 조회 복구 수정까지 포함한 최종 타입 검사·변경 파일 lint·운영 빌드도 통과했다(`step734-types-release.log`, `step734-lint-release.log`, `step734-build-release.log`). 확장 코드·권한·DB migration은 바꾸지 않았다.

### 최초 통합 검사에서 발견한 테스트 문제

최초 46파일 검사는 401건 중 386통과·15실패였다. 이 결과와 소스 1,356개 SHA가 검사 동안 바뀌지 않았다는 근거는 `step734-related-closure-{freeze,proof}.json`과 `.log`에 그대로 보존한다. 실패를 통과로 집계하거나 최초 로그를 덮어쓰지 않았다.

견적 제목 4건은 이번 변경 모듈을 읽지 않는 기존 경로에서 발생했다. 실제 HEAD의 runtime bytes를 읽는 격리 fs overlay와 수정하지 않은 같은 시험 파일에서도 동일한 4실패를 재현했다. 앱·운영 파일을 checkout/reset하지 않았다. 유효한 SEO 문서 정책의 상품 제목과 독립적인 6개 옵션 UUID·옵션 이름을 구분하도록 기대값을 수정했다. 기존의 옵션 접미사 XLSX 검증은 삭제하지 않고, 실제 일반 content 제목 PATCH로 SEO 문서 정책이 무효화되는 다음 상태에서 그대로 검증한다. 수정한 8건은 모두 통과했다(`step734-title-baseline-proof.json`, `step734-title-flow-repair-proof.json`).

이미지 재연결 8건은 변경한 6단계 저장기가 아닌 기존 7단계 경로의 시간 초과였다. 대표 한 건은 HEAD 상태에서도 동일하게 재현했고 이번 변경 production 파일 로드는 0이었다. 대기 중에도 1ms마다 전체 화면을 강제 렌더하던 fixture를 실제 React처럼 Object.is 상태 변경 때만 렌더하도록 고쳤다. 명시적 render는 여전히 강제 렌더하며 20초 대기 제한·실제 component/API/암호화·오류 처리는 그대로 유지한다. 그 뒤 드러난 이전 PNG 참조 기대값도 기존의 영수증 검증을 거친 동일 옵션 라벨 교체 규칙에 맞췄다. 수동 참조·다른 5개 옵션·이전 pool/object bytes는 유지되며, 실제 XLSX와 최종 7개 파일의 plan/bytes가 현재 참조와 일치하는 것을 검사한다. 8건 모두 통과했다.

나머지 3실패는 저장 응답 유실을 정확한 GET으로 즉시 복구하는 새 동작과 이전 callback 기대값의 차이, 저장 중 숨겨진 폼을 저장 후 화면으로 다루던 기대값이었다. 단순히 입력 개수를 줄여 통과시키지 않았다. 저장 중 busy·폼 숨김, ACK 후 9개 편집 항목과 기존 입력, 구조 쓰기 없음, 다른 옵션·unmount의 늦은 callback 거절을 검사한다. PUT 뒤 복구 요청은 GET뿐이며 추가 텍스트 PUT은 없는 것도 확인한다. 관련 두 파일 10건은 모두 통과했다(`step734-label-repairs-proof.json`).

위 15건의 복구까지는 테스트와 fixture만 추가 변경했으며, 앞서 빌드한 production 4파일의 SHA는 그대로였다. 변경한 fixture를 사용하는 12개 시험 파일까지 다음 검사 범위에 포함했다. 제목·fixture·재연결 기대값 수정은 별도 담당이 최종 SHA로 독립 검토했다. 위 집중 검사 수는 서로 및 최종 통합 검사와 겹치므로 더하지 않는다.

### 범위를 넓힌 검사에서 발견한 실제 복구 잠금

다음 56파일 검사는 485건 중 463통과·22실패였다. 이 결과와 소스 동결 근거는 `step734-related-final-{freeze,proof}.json`과 `.log`에 보존한다. 실패는 추가로 포함한 세 라벨 오류/혼합 연결 파일에서 나왔다. 저장 응답 누락을 즉시 조회해 복구하는 기존 동작, 같은 옵션에서 영수증으로 확인된 이전 생성 PNG를 교체하는 규칙과 맞지 않는 기대값이 있었다. 수동 이미지·다른 옵션·이전 파일 객체의 보존 검증은 유지한다.

동시에 실제 앱 오류도 확인했다. 이미지 처리 오류 뒤 최신 견적 조회까지 실패하면 `labelRecovery`가 남는다. 이 상태를 전체 `busy`에 포함하면서 유일한 명시적 조회 버튼도 막아, 다시 조회해 복구할 수 없었다. 자동 조회나 데이터 쓰기를 추가하지 않고 기존 **기본값 다시 반영**의 읽기 전용 재시도만 열도록 수정했다. 진행 중 작업·옵션 분리는 계속 막는다. 복구 잠금 상태에서는 미저장 수정·충돌도 계속 막고, 일반 재조회는 기존 입력 조정 동작을 유지한다. 옵션·화면·수정값·복구 상태가 달라진 오래된 callback과 이중 클릭도 무시한다. 내부 오류 복구 조회는 기존 작업 잠금 아래에서도 실행되는 계약을 유지한다.

추가 담당의 29건 집중 검사는 최종 전체 검사와 중복되지 않게 중단했다. 부분 로그 `step734-label-consumer-repairs-final.log`의 7개 batch 통과만 확인했으며 전체 완료/통과 수로 집계하지 않는다. 최종 57파일 검사에는 이 29건을 모두 포함한다.
