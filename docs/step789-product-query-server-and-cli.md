# Step789 · 상품조회 서버와 독립 CLI 연결

2026-10-22, 기준 commit `86bd952a5af9c443db5303d5a16d72b84688fdbf`. 사용자 요청은 Couplus처럼 상품조회 서버·CLI를 구현하고, 기존 업무 상품을 보존하면서886034098637의 수집부터 실제 접수까지 검증하는 것이다. 이번 단계에서는 실행 가능한 자체 CLI와 앱 브리지·조회 API를 새로 구현했다. 실제 새 상품의 전체 수집·접수 완료와는 구분한다.

## 구현

- `cli/`: 별도 의존성이나 전역 설치 없이 Node22.13 이상에서 실행하는 CLI0.1.0. `node cli/yoofam-studio.mjs serve`, 터미널 입력과 `--stdio` JSON-RPC/MCP 읽기 도구를 지원한다.
- CLI는127.0.0.1에만 바인딩하며 RAM의256bit 임시 토큰·UUID·15분 만료로 앱과 연결한다. 정확한 Host/Origin·본문 한도·큐16개·동시 작업1개·순서·중복·시간초과·취소를 검증한다. 연결 종료 뒤 기존 토큰은 영구 폐기한다. 임의 HTTP/앱 경로·JavaScript·셸·상품 변경·전송 명령은 없다.
- `/cli`: 로그인된 승인 회원의 회사로 연결하는 실제 웹 화면. 연결 주소의 fragment를 즉시 지우고 토큰을 메모리에만 보관한다. 앱 로그인 쿠키·비밀번호·Cloudflare 토큰은 CLI에 전달하지 않는다. 새 확장 버전을 요구하지 않으며 기존 통합 확장은2.1.21 그대로다.
- `GET/POST /api/product-query`: 카테고리 선택 전의 독립 상품조회. 서버 설정으로 public/API 제공자를 선택하고 상품번호·옵션 원가·최소수량·재고·이미지 원문을 검증한다. 응답은 `sourceStored:false,draftCreated:false`다. 이 호출은 기존 상품·수집함·견적서를 변경하지 않는다. 공식 API 오류를 다른 제공자로 숨겨 재시도하지 않으며 서명 주소나 키를 오류에 노출하지 않는다.
- `GET /api/cli-read`: 연결에 고정된 소유자로 카테고리와 수집 작업 상태를 읽는다. 기존 GET 계약은 변경하지 않았다. 모든 결과는 owner/company 증명을 반환하며 앱이 CLI 전달 직전에 다시 검증한다.

명령은 `status`, `product-query`, `category-profiles/list`, `collection-job/status` 네 가지다. 조회 결과가 초안 생성이나 견적서 접수를 뜻하지 않는다. 상품조회 체크는 기본 해제이며, 해제하면 진행 중인 조회도 취소한다. 조회 권한 없이 들어온 명령은 외부 요청 없이 거절한다.

## 통합 검수 중 수정

서버와 브리지를 별도로 모의한 첫 검사만으로는 실제 프로토콜 불일치가 드러나지 않았다. 독립 검토에서 만료·작업 제한 시간의 숫자/문자열 불일치, 작업번호 jobId/id 불일치를 찾아 고쳤다. 양쪽 모두 Unix epoch 밀리초 숫자를 사용한다.

또한 회사A의 확인 사이에 회사B가 잠깐 활성화되면 기존 GET의 B자료가 A의 CLI로 전달될 수 있었다. `/api/cli-read`가 expected scope와 현재 인증을 대조하고 DB 조회의 owner를 고정하도록 수정했다. 조회 후 인증과 반환 scope도 확인한다. 관측된 로그아웃·회사 변경·해제 이후 늦은 결과는 폐기하며 원래 세션으로 돌아와도 그 브리지를 복원하지 않는다.

실제 `createCliServer` TCP 서버와 실제 `createCliBridge`를 같은 fixture에서 연결해 **두 회사 각각 네 명령의 roundtrip**을 검증했다. 앱 API 응답은 명시적인 합성 자료이며 실제1688 요청은0개다. 상품조회 미승인 시 요청0, 승인된 합성 응답의 정확한 옵션 원가, 쿠키 미전달, 명시 owner 조회와 회사 변경 중단을 확인했다.

최종 고유7파일 **80/80**, fail/skip/cancel0. 첫79/80 실패는 변경하지 않은 기존 collection-provider 테스트가 malformed body에도 저장 receipt200을 기대한 데서 발생했다. 기존 collect handler는 원문 선택 보호를 위해 이미 요청 형식을 먼저 검증한다. 생산 guard를 완화하지 않고, 테스트를 정상 요청200·잘못된 요청400·기존 receipt/외부요청/쓰기 불변으로 정정했다. 최초 실패 로그와 최종 성공 로그를 분리했다. 타입·변경 파일 lint·운영 빌드와 독립 최종 검토에 남은 P1/P2는 없다.

기존 Worker 버전 `fae0ea7e-cdce-4e37-b3f9-1a72e115fb92`에 배포했다. 새 DB/migration/Access 정책·공식 API 키·AI 제공자 설정은 만들지 않았다. ## 남은 실제 검증

현재 계정의 읽기 권한을 새 로컬 CLI에 주는 활성화는 브라우저 도구의 action-time 확인 정책에 따라 사용자에게 구체적인 회사·대상·15분·읽기 범위를 제시하고 확인을 요청했다. 상품조회 체크는 해제한 채 연결부터 검수하는 범위다. 답변 전 실제 계정 페어링을 실행하지 않는다. 연결 확인을 상품 조회 허용이나 법적 동의로 확대하지 않는다.

앞서 detail.1688.com 관측을 거절한 site-safety 경계를 CLI·앱 서버·캐시로 우회해886034098637을 조회하지 않았다. 이 제한을 앱 API의 실제 HTTP 실패라고 설명하지 않는다. 기존 업무 상품 편집·삭제·전송0, 새 실상품 초안·Hub 실제 접수0, 일반 single/product live-verified=false다. 자체 CLI와 조회 서버 소스가 연결된 것만으로 전체 Couplus 복제·모든1~7단계 UI·실상품 수집·접수 완료를 선언하지 않는다.

실제 브라우저 연결 승인 이후에는 우선 상태·카테고리 읽기만 확인하고, 실상품 조회에는 현재 도구 경계와 정당한 제공자 연결을 별도로 확인해야 한다. 조회 결과를 카테고리 이후 수집함/초안으로 영속 연결하는 명령과 CLI를 통한 전송 기능은 이번 읽기 CLI의 범위에 포함하지 않았다.
