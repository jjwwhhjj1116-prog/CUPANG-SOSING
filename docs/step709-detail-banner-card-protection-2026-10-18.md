# Step709 — 상세 이미지 단건 카드의 설정 배너 보호

기준 HEAD는 `4d77641`이다. 기존 작업 상품·브라우저·외부 사이트를 열거나 변경하지 않았다. 이번 범위는 상세 단계의 개별 카드 조작과 같은 슬롯의 이미지 번역/편집 API다. 원본 확인은 이미 보관한 Couplus 자료와 좁은 REA 정적 render 근거를 사용했다.

## 문제와 변경된 동작

기존 `OptionImageEditor`는 설정 상단·하단의 `protectedDetailImageKeys`를 Delete 단축키에만 적용했다. 같은 배너의 삭제·이동·드래그·중국어/영어 번역·편집 버튼과 후보 체크는 계속 실행할 수 있었다. 기존 일괄 번역과 작업 구성 편집기에서는 이미 보호하던 자료였다.

이제 상세 카드의 버튼·후보 체크·실제 콜백에서 같은 역할 증거를 확인한다. 배너를 삭제하거나 번역/편집 대상으로 전달하지 않는다. 본문은 배너 사이에서 정렬·삭제·편집할 수 있고, ‘본문 이미지 선택 비우기’는 배너를 남긴다. 본문 드래그가 배너를 넘어가는 것도 막는다. 배너를 숫자 위치에 고정하지 않으므로 본문 삭제에 따른 마지막 배너의 인덱스 변화는 허용한다. 공통·자동값 복원은 별도의 명시 동작으로 유지한다.

카드의 숨은 단계·상품 버전·프로필·옵션·잠금 상태가 바뀌었다 돌아오더라도 이전 콜백을 다시 쓰지 않는다. 자동 조회는 카드 조작 세대와 분리해 저장 후 최신 자료를 계속 읽고, 숨겨진 단계의 기존 초기 읽기도 유지한다. 렌더의 드래그 가능 여부는 React 상태로 계산하고 실제 제스처에서 별도 live 검사를 한다.

`image-text`의 상세 견적 원본 발급도 현재 보호 배너를 거절한다. 저장한 편집 문서 재열기, 직접 보낸 번역 요청과 PNG 적용도 같은 검사를 거친다. 추가 이미지·대표 이미지·라벨의 기존 대상 규칙은 바꾸지 않는다. 과거 요청의 `POST recover`는 기존 결과의 읽기 확인만 허용하며, 그 확인으로 새 번역·적용 대상이 되지는 않는다. 기존 파일·상품 원문·공통 역할·다른 옵션을 자동으로 바꾸거나 삭제하지 않는다.

역할 증거가 없거나 손상되면 상세 카드의 이미지 변경은 잠그고 HTML 직접 입력은 유지한다. 배너만 남아 새 본문의 위치를 확인할 수 없는 목록에서는 파일명으로 상하단을 추측하지 않고 공통·자동값 복원 안내를 표시한다. 일반적인 본문 추가는 마지막 본문 뒤·보호 배너 앞에 넣는다.

## 검수

최종 집중 검사4파일의 서로 다른73개 검사가 모두 통과했다. `option-detail-keyboard.test.mjs`18개(신규8개), `option-image-editor.test.mjs`22개, `free-image-quotation-linkage.test.mjs`21개, `detail-image-batch-banner.test.mjs`12개다. 초기 실패·복구 집중 실행은 중복 합산하지 않는다. 결과는 `outputs/step709-detail-banner-tests.log`, `outputs/step709-detail-banner-protection-proof.json`, `outputs/step709-detail-banner-final-proof.json`에 기록한다. 합성 React scheduler·인증/회사·이미지와 격리 SQLite/R2 아래 실제 컴포넌트 콜백·로컬 API를 사용한다. 실제 브라우저 픽셀, OCR/번역 품질, 신규 1688 수집과 Supplier Hub 접수 증거는 아니다.

초기 실패 로그와 fixture 보정 과정은 별도로 보존했다. 과거 배너 결과 검사는 새 서버에 과거 proof를 발급시키는 대신 fixture 내부에서만 이전 발급기를 명시적으로 재현한다. 모바일 풀 fixture의 IEND 뒤 식별 바이트는 이미지 API 검사에 맞는 완전한 합성 PNG로 교체했다. 기존 UI harness는 render 중 상태 변경을 React처럼 안정시킨 뒤 이벤트를 실행하도록 보정했다. 서버 읽기 복구가 새 보호 규칙 때문에 막히던 연결은 쓰기 권한을 열지 않는 `readOnlyRecovery` 경로로 분리했다.

변경 코드와 집중 검사 파일의 ESLint는 384MB heap에서 오류·경고 없이 통과했다. 최초 192MB 실행의 메모리 부족 로그는 보존했으며 코드 오류로 계산하지 않는다. 넓은 타입 검사·빌드·배포는 root 담당이며 이 작업자가 실행하거나 완료로 주장하지 않는다.
