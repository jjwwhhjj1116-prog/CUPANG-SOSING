# Step731 — URL 수집 방식 선택과 초기 견적서 기본값 검수

2026-10-19. 기준 commit `05bd72ef9cf8d72bf36c43f60f88803a4c615718`. 기존 작업 상품·회사 설정·운영 견적서는 변경하지 않았다. 이번 변경은 실제 새 1688 상품의 수집 성공이나 Supplier Hub 접수를 입증하지 않는다.

## 수정한 수집 결함

열린 상품 탭의 사전 조회가 성공하면 클라이언트가 곧바로 `/browser-capture`에 원문을 저장했다. 서버의 명시적 API 설정을 읽는 코드는 `/collect`에만 있어, 설정된 API가 있어도 이 조회를 건너뛸 수 있었다. 조회 방식에 따라 옵션·상세 원문이 달라질 수 있는 결함이다.

새 요청은 사전 조회 결과가 있을 때도 `/collect` 한 번으로 들어간다. 원문 후보는 크기가 제한된 `{browserCapture: ...}` 본문으로 전달한다. 서버는 기존 불변 원문을 먼저 반환하고, 새 수집에만 서버 설정으로 공급자를 선택한다. API가 설정돼 있으면 후보 내용으로 공급자를 바꾸지 않고 API의 검증 결과를 사용한다. 공개 페이지 방식일 때만 기존 브라우저 원문 parser로 후보를 검증해 저장하므로 불필요한 외부 조회가 없다. 후보가 없는 구버전 요청의 빈 본문도 계속 지원한다.

설정 오류, API 실패(`SOURCE_PROVIDER_FAILED`), 잘못된 후보(`SOURCE_CANDIDATE_INVALID`)는 명시적인 실패로 남긴다. 이 경우 Chrome 수집으로 자동 전환하지 않는다. 공개 페이지 조회 실패만 기존 명시적 Chrome 대체 경로를 사용한다. 저장 응답을 잃었을 때는 같은 작업의 원문 GET 한 번으로 확인하며 수집 쓰기를 경쟁 실행하지 않는다. 선택적 원문 보완을 생략할지는 제출한 후보가 아니라 실제 저장된 공급자로 판단한다.

스키마·회원정보·확장 권한·새 외부 서비스·네트워크 경로는 추가하지 않았다. 준비 확장은 이전과 같은 0.2.81이다.

## REA와 원문 증거의 경계

[Step729](step729-rea-acquisition-contract.md), [Step730](step730-source-first-2026-10-19.md)의 보관 분석을 재사용했다. Couplus 클라이언트는 자체 `/api/aiPage/getProductInfo`를 호출하지만 해당 클라이언트와 CLI 자료가 그 서버의 상위 공급자·인증·캐시 구현을 포함한다는 증거는 없다. 보관 REA bundle의 정적 record는 13개, 네트워크 capture는 0개다. 자체 OpenAPI 후보의 합성 응답 검사로 Couplus의 실제 공급자가 확인됐다고 주장하지 않는다.

보관된 실제 공개 원문 fixture는 현재 parser가 이미 지원한다. 동일 offer의 모바일 초기 데이터·SKU·상세 자료는 SKU 6개·이미지 19개·속성 24개로, 독립 SKU 자료는 SKU 6개·이미지 4개로 해석됐다. 이번에 추가로 지원해야 할 완전한 새 성공 응답 형식은 발견하지 못했다. 이는 과거 자료를 해석한 결과이며 새 URL을 현재 조회했다는 증거가 아니다. 파일별 SHA와 한계는 `outputs/step731-retained-source-audit.json`에 있다.

## 초기 소재 고시 검사 정정

처음 넓힌 회귀검사는 194건 중 187통과·7실패였다. 실패한 세 테스트 파일을 정확한 이전 runtime 세 파일로 되돌린 별도 프로세스에서 실행했을 때도 같은 7건이 실패했다(41건 중 34통과). 작업 트리나 운영 DB를 되돌리지는 않았다. 원본 로그와 과정은 `outputs/step731-baseline-material-{proof.json,log}`에 보존했다.

이 실패는 새 URL 초안의 소재 고시가 원문/라벨 소재를 자동으로 따른다는 오래된 기대값 때문이다. [Step700의 원본 분석](step700-initial-legal-notices-parity-audit.md)에서는 초기 법적 고시 기본값과 6단계 라벨 저장을 구분한다. 6단계 표시사항을 저장하는 메서드는 라벨 이미지를 연결하며 법적 고시를 다시 쓰지 않는다. 7단계에서 직접 입력한 공통/옵션 고시와 공란은 우선한다. 따라서 런타임 기본값을 바꿔 검사를 맞추지 않는다. 원문·라벨 소재를 보존하는 검사와 초기 고시 기본값, 실제 7단계 수정값, 표식 없는 기존 데이터의 연결 검사를 분리해 유지한다.

## 실제 접근과 남은 검증

공식 개발자 안내 `https://open.1688.com/`를 기존 Chrome4에 여는 동작이 자동 승인 검토에서 거절됐다. 검토 이유는 앞선 1688 접근 거절 이후 다른 도메인 접근을 반복했고, 일반적인 “계속 진행”만으로는 그 접근을 다시 승인한 것으로 인정하지 않는다는 것이다. 페이지는 열리지 않았다. 사이트 로그인 오류를 관찰한 것이 아니다. 이후 다른 도구·도메인·확장으로 재시도하지 않았다.

지정 상품 `https://detail.1688.com/offer/1022260303756.html`의 상품정보 읽기와 위 공식 개발자 안내 읽기만을 구체적으로 재승인하는 질문을 보냈다. 수정·구매·결제·약관 동의는 제외했다. 응답 대기 중이며, 그동안 소스 수정과 오프라인 검사를 진행했다. `outputs/step731-access-boundary.json`에 기록했다.

실제 새 URL 수집, 실제 Supplier Hub 문서 작성·약관·제출·접수번호·SKU 연결은 미검증이다. 두 native live gate는 계속 false이며 합성 검사 통과로 해제하지 않는다. 기존 작업 데이터로 이를 대신 검증하지 않는다.

## 최종 검사와 기존 배포 반영

수집 분기의 집중 검사는 82/82, 초기 고시·소재 경계의 정정 검사는 44/44 통과했다. 이 숫자를 중복 합산하지 않는다. 마지막 통합 실행은 관련 16개 파일의 **197/197** 통과이며 실패·취소·skip은 0이다. 검사 전후 app/db/확장/scripts/tests 1,348개 파일의 SHA는 같았다. 타입 검사, 변경 소스·테스트 lint, 운영 빌드, 기존 확장 ZIP 일치 검사도 통과했다. 독립 검토의 세 runtime 파일 SHA가 마지막 검사와 일치한다. 최초 194건 실행의 7실패 기록과 이전 버전 재현 기록은 덮어쓰지 않았다.

최초 배포 요청은 자동 승인 검토가 7건의 회귀 실패를 이유로 실행 전에 거절했다. 위 원본 규칙 검토·기대값 정정·197/197 최종 검사로 그 조건을 해소한 뒤 **동일한 배포 명령**으로 재요청했고 성공했다. 우회 도구·대체 배포 경로는 사용하지 않았다. 기존 Worker의 새 version은 `c4828c20-2b52-4054-bd0e-72f0eb883318`이며 배포 주소는 `https://sourceflow.jjwwhhjj1116.workers.dev/`다. DB migration, 회사 설정·회원·상품 쓰기, 새 권한 부여는 하지 않았다.

주요 검사 근거는 `outputs/step731-provider-proof.json`, `step731-independent-review.json`, `step731-material-contract-tests.log`, `step731-related-closure-{proof,freeze}.json`, `step731-final-validation.json`이다. `step731-deploy.log`는 기존 Worker 업로드와 triggers 배포 성공을 기록한다. 배포 성공을 실제 상품 수집·견적서 접수 성공으로 해석하지 않는다.

배포 뒤 같은 Chrome4의 자체 앱 확인 탭에서 관리자 계정 표시, 상품 목록 로딩 완료, 콘솔 오류 0을 확인했다. 상품/설정을 열거나 원문 조회·전송을 시작하지 않았다. 읽기 증거는 `outputs/step731-production-proof.json`, 화면은 `step731-production.png`이며 확인 탭은 닫았다. 원래 Couplus/Hub 작업 탭은 그대로 두었다.
