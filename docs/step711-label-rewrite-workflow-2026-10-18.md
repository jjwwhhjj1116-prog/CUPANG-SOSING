# Step711 — 표시사항 재작성과 새 생성 PNG 연결

기준 `0d9f9491ccaa4f3e091cb5cf0d558151359067f0`. 보관 원본의 완료 화면과 `resetLabels`는 `step711-label-rewrite-parity-audit.md`, 저장 API는 `step711-label-rewrite-api-2026-10-18.md`, PNG 증빙은 `step711-label-rewrite-proof-2026-10-18.md`에 구분했다. 기존 실상품·회원·공유 Chrome·운영 DB는 조작하지 않았다.

원본 재작성은 root와 모든 옵션의 생성 이미지/상태를 초기화한다. 표시사항 값·구조·견적 파일 참조를 비우거나 물리 파일을 삭제하는 요청은 아니다. 자체에는 같은 생성 상태 필드가 없어 optional `renderEpoch`로 재작성 이후의 생성물을 구분한다. 원본이 이 counter를 사용한다고 주장하지 않으며, 전체 완료/편집 화면 분기까지 픽셀 동일하게 만들었다는 뜻도 아니다.

## 동작

- 표시사항 화면의 **표시사항 재작성**을 누르면 상품 공통과 모든 옵션에 적용됨을 확인한다. 직접 입력·최종 라벨 선택이 미저장 상태이거나 저장 중이면 실행할 수 없다. 취소하면 요청·PNG 캐시·저장본이 그대로다.
- 확인 후 명시적 POST 한 번으로 현재 원문·회사·카테고리·설정·옵션·견적·라벨 버전을 확인하고 생성 세대만 올린다. 입력값·항목 순서·공통/옵션 공란·견적 참조·원본 파일을 보존한다. 이후 보통의 값·구조 저장과 이전 내부 호출도 이 세대를 유지한다.
- 재작성 전 서버 증명 PNG는 내용이 같더라도 다시 생성·연결해야 한다. 새 세대의 업로드 ID와 증빙을 사용하며, 예전 파일은 삭제하지 않는다. 수동 업로드 등 이 생성 증명이 없는 파일을 파일명으로 추정해 무효화하지 않는다. legacy 자료는 marker가 없어 기존 recipe를 정확히 유지하고 자동 이관하지 않는다.
- 요청 응답이 유실되거나 저장 후 조회가 실패하면 결과 확인을 제공한다. 오류 응답 코드만으로 미저장이라 판단하지 않는다. 확인 버튼은 GET만 실행하고, 정확한 저장 결과 또는 정확한 미변경 상태를 확인한다. 다른 변경과 섞였으면 새 POST를 자동 재시도하지 않는다. 명시적인 최신 저장본 조회도 가능하다.
- 오래된 클릭·드래그·다른 옵션/원문으로 바뀐 응답·unmount는 현재 편집에 적용되지 않는다. 결과가 불확실한 동안 주 표시사항과 자식 라벨 저장을 함께 잠그며 읽기 확인은 가능하다.

## 검수

주 UI/실제 client callback 신규9개는 확인 취소, 명시 재작성·동일 문구 새 PNG, 유실 ACK, 불확실 결과, 미도달 요청의 GET 확인, 커밋된503/409 후 조회 장애, 미저장 입력·참조 선택, 중복 클릭·옵션 변경·unmount를 검사한다. API·브라우저 confirm·hook scheduler·PNG는 합성이며 사용자 브라우저 포인터 검증이 아니다.

초기 UI7실패는 기존 테스트 fixture가 URL 생성자 대신 미리보기용 static object만 제공한 한계였다. 실제 URL 생성자를 제공한 뒤 남은 옵션 전환 fixture 한 건도 새 옵션 조회가 끝나기 전에 이전 요청을 커밋하던 순서를 정리했다. 앱의 버전 충돌 보호를 완화하지 않았다. 독립 읽기 검토에서 발견한 ‘저장 후 오류 응답+조회 장애’를 불확실하게 유지하도록 수정했고503/409를 모두 회귀 검사했다.

API 검사는 양사 격리 SQLite/D1·R2와 실제 자체 route handler를 사용한다. legacy 부재, 첫/두 번째 세대, 중복 요청409, 일반 PUT/내부 호출 보존, 원문 경합, 다른 회사/사용자·인증·origin·본문·저장 한도·overflow·클라이언트 epoch 주입 거절을 검수한다. 최종 고유 검사 수·소스 SHA·타입/린트/스키마/빌드·배포 결과는 `outputs/step711-final-validation.json`에 고정하며 focused 반복을 더하지 않는다.

실제 자체 Single 준비까지 잇는 격리 검사에서 공통 PNG를 상속한 옵션이 새 생성물을 붙여도 이전 공통 파일을 계속 포함해 차단되는 오류를 재현·수정했다. 현재 세대가 양수이고, 이전 공통 생성 증명의 세대가 다르며, 모든 연결 필드의 옵션 직접값이 없고 공통·현재 해석값이 정확히 같은 경우에만 새 옵션의 직접 목록에서 이전 공통 생성 참조를 교체한다. 저장된 공통 참조·파일은 보관한다. 같은 세대·옵션에서 직접 재선택한 공통 파일·수동 파일·다른 카테고리/프로필은 자동 제거하지 않는다. 배치 사전검사·복구에도 같은 세대 계약을 반영했다.

양사 각각 재작성 직후2옵션 차단 → 첫 옵션 재생성 뒤 나머지1옵션 차단 → 둘 다 재생성 뒤 준비 가능을 확인했다. 실제 자체 renderer·파일 업로드/조회·새 세대 receipt·첨부 API·Single 패킷의 정확한 URL과 media 바이트를 대조했다. canvas/PNG·원문·양식은 합성이며 글꼴 픽셀이나 원격 수락 검사가 아니다. 포함 옵션의 Single 라벨 한 장 제한을 완화하지 않았다. 수동 파일 보존은 제외 옵션과 별도 선택 계획에서 검사했다.

최종 **19개 고유 테스트 파일142/142 통과**, 신규20개 포함, 실패·취소·건너뛰기0,81.15초다. 실행 전후 소스/설정/테스트1278개 SHA가 동일하고, 과거/독립 증빙5개의 바이트·수정 시각을 복원해 이번 실행 증거9개를 별도 보관했다. 전체 타입768MiB, 앱/DB·변경 테스트 린트384MiB, 스키마44테이블17인덱스29모듈과 제한 메모리 운영 빌드가 통과했다. 전체 저장소 검사 수로 확대하지 않는다. 최초 pure33 검수는 좁은 첨부 수정 전의 역사 해시를 그대로 보관하며, 최종142 검수가 현재 소스를 고정한다.

## 범위

이 기능이 실제 신규1688 수집·모든 카테고리 양식·Supplier Hub 접수번호/SKU 발급까지 완료됐다는 뜻은 아니다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`와 기존 운영 전송 gate는 유지한다. 새 유료 공급자·자원·DB migration·확장 버전 변경은 없다.
