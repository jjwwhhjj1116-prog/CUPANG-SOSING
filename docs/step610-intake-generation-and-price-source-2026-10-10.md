# Step610 — 최신 수집 입력 저장과 가격 원천 검수

## 수집 대기열 자동저장

이전 저장 콜백이 실행되면 최신 generation과 이전 URL·목표를 한 요청으로 묶어 보낼 수 있었다. 재현에서는 화면 목표가 `work`, 실제 저장 목표가 `price`인데도 최신 입력을 저장한 것으로 표시하고 자동저장을 중단했다.

현재 행·목표·generation을 하나의 ref snapshot으로 읽어 저장하도록 수정했다. 저장 중 추가 입력은 계속 미저장 상태로 유지한다. 오래된 타이머·콜백도 현재 입력을 저장하고, 종료된 컴포넌트의 콜백·setter는 동작하지 않는다. 기존 응답 유실 복구와 CAS·실제 서버 저장 결과 확인은 유지한다. 두 승인 회사의 실제 draft API와 임시 SQLite를 포함한 회귀로 검증했다.

## 기본설정과 가격 단계 대조

같은 기존 Chrome의 쿠플러스 기본설정과 2단계 가격 폼을 읽기 전용으로 대조하고 화면을 보관했다. 일반 환율은 통합통관을 사용할 때도 보이며 번들 수량 선택에 사용된다. 앱에서 이 입력을 숨기던 차이를 수정했다. 일반 환율과 통합통관 환율은 서로 독립적으로 편집·저장하며, 각각 번들 수량과 통합통관 매입가 계산에 적용한다. 설정이나 기존 상품을 실제로 변경하는 작업은 이 대조에서 실행하지 않았다.

계산식은 변경하지 않았다. 통합통관 원가는 `(단품 CNY × 판매 구성 수량 × 통합통관 환율 + 200 + 100) × 1.1`을 원 단위 반올림하며, 일반 환율은 별도의 번들 수량 선택에 사용한다. 사용자 설정은 저장할 때만 적용되고 기존 상품과 접수된 요청의 가격 정책은 유지한다.

## 가격 표기와 수량 검수

기존에 판매가가 공급가 이상이어야 한다고 확인된 분류에서 `1e4 / 9e3`은 정수 숫자로 내보내면서도 가격 관계 검사에서는 빠졌다. 실제 API·SQLite·XLSX·확장 파일 준비로 오류 0개와 잘못된 가격 조합을 재현했다.

확인된 가격 관계 규칙은 허용된 숫자 표기 모두를 실제 필드·내보내기와 같은 방식으로 해석해 비교한다. 허용된 0원 wire도 비교한다. 개별 필드의 문법·범위·소수점 제약, 직접 저장한 원문·공란·OSRP는 유지한다. 원문 근거가 없는 다른 카테고리로 규칙을 확대하지 않았다.

7단계 canonical 수량을 직접 바꿔도 자동 가격은 2단계의 판매 구성 수량으로 계산된다. 실제 재현은 `3개입 / 공급가 7560 / 판매가 12600`의 수량만 `1`로 바꾼 경우였다. 자동 계산 가격 셀에 해당 계산의 구성 수량을 검토 정보로 표시하고 편집 화면·제출 검토·XLSX 경로까지 연결했다. 자동 재계산이나 강제 수량 변경은 하지 않는다. 수동 가격·직접 공란과 다른 옵션의 입력은 유지하며, named Hub 수량은 다른 의미일 수 있어 비교하지 않는다. 수량을 편집 중인 경우에는 이전 저장값의 검토 메시지를 숨기고 저장 후 다시 계산한 검토를 표시한다.

편집기는 값·원천이 동일한 저장 셀의 검토 정보를 보존한다. MSRP의 별도 가격 근거 검토와 수량·가격 원천 검토도 함께 표시한다. 오류를 검토 정보로 낮추거나 등록 완료로 처리하지 않는다.

## 검사 범위

회귀는 임시 저장소·합성 상품·기록된 원문을 사용한다. 운영 상품·쿠플러스 등록 자료·기존 입력 대기열을 수정하지 않는다. 신규 실제 1688 수집과 모든 카테고리의 동일성 및 Supplier Hub 신규 접수 완료 검증은 별도 남아 있다.

최종 검사: 수집·대기열 92개, 가격·기본설정 177개, 견적 편집·제출 준비 267개로 **536/536 통과**. 실패·취소·건너뛰기 0개, TypeScript 오류 0개, ESLint 오류 0개(기존 경고 8개), 운영 빌드 검사 통과. 17개 마이그레이션과 확장 0.2.57/0.2.58 파일 지문은 이전과 동일하다.
