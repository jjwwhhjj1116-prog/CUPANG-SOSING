## 수집한 일반 속성이 견적 AI에 빠지던 연결 수정

원본의 견적 AI 요청은 일반 상품 속성 전체를 참고한다. 자체는 수집 원문 번역 후 `content.categoryAttributes.values`에 저장하고 양식의 정확한 필드로도 연결하지만, AI 참고자료에는 표시사항 속성7개만 넣었다. 예를 들어 실제 resolver가 `호환 기종: 전용기기-706A`를 읽으면서도 AI 요청은 이 값을 전달하지 않았다. 모델의 실제 오답이나 운영 저장 오염을 관측한 것이 아니라, 저장본→요청 자료의 누락을 격리 재현한 것이다. 원본 함수·SHA와 before probe는 `step706-source-draft-parity-audit.md`에 있다.

`buildQuotationAiPlan`은 같은 카테고리에 연결된 서버 생성 속성만 추가 참고자료로 전달한다. 이름·값·선택적 원문 이름을 보존하고 `category-source-translation` 출처로 기존 label 사실과 구분한다. 서로 같은 이름인 값도 순서·출처를 유지하며 덮거나 하나로 합치지 않는다. 원문 이름은 설명이며 옵션 고유번호나 field binding 권한이 아니다.

다른 카테고리의 예전 속성은 가져오지 않는다. 기존 `bindings`의 필드 정의 서명 검증을 해석하거나 완화하지 않고, 수동 공통·옵션 수정값과 공란도 보호한다. 최대50개, 번역 계약의 이름200자·값2,000자·원문 이름200자, primitive 문자열·제어문자를 검증한다. 내부 속성이 잘못됐으면 resolver·AI 실행 전 명확하게 거절한다. 기존 prompt64KB·전체 plan768KB 한도와 AI 모델·출력·하루 요청 한도는 유지한다.

실제 API의 생성 요청 fingerprint는 전체 stablePlan을 포함하므로 참고자료가 새 요청의 식별값에도 들어간다. 저장값이 바뀌면 이전 검토 요청은 모델 호출 전에 거절되며 명시적인 새 검토만 새 자료를 사용한다. 이미 완료된 과거 AI 이력을 자동으로 지우거나 재실행하지 않는다. 기존 프로필·상품·옵션·가격·인증·물류·동의·전송 상태에 자동 쓰기는 없다.

## 공식 단일 견적 양식의 같은 URL 새 초안 경로

같은 URL의 기존 작업과 현재 카테고리·기본설정이 다르면 기존 상품을 보존하고 새 초안 검토를 제공하는 경로가 이미 있었다. 그러나 UI 복구 버튼과 서버가 Excel template만 요구하여 `Retail_Categorized_Single`, `template:null`인 정상 단일 양식에서는 진행할 수 없었다. UI 버튼만 표시해도 서버가409로 거절하는 것을 두 회사의 실제 로컬 API/SQLite에서 먼저 재현했다.

기존 workbookEvidence와 저장 Excel 검증 경로는 그대로다. template이 정확히 null인 경우에만 별도 단일 양식 검증을 허용한다. 현재 회원 회사·카테고리 코드와 경로·내부 카테고리/고시/버전/scope metadata의 별칭·원문 metadata가 모두 일치하고 컴파일 불가 규칙이 없어야 한다. 불완전한 Excel이나 이름만 비슷한 비공식 schema를 단일 양식으로 바꾸지 않는다.

복구 버튼으로 저장된 원문을 검토한 뒤 명시적으로 새 초안을 만들면 새 요청/상품 ID를 사용한다. 선택한 카테고리와 현재 회사별 기본설정으로 연결하며 기존 상품·수동 수정값·원문 영수증·private 이미지와 전송 이력은 유지한다. 중복 클릭·응답 유실은 같은 요청 ID로 복구하고, 다른 owner/회사·카테고리/설정 변경·취소/진행 중인 작업은 기존 경계에서 거절한다. 별도의 실제 사이트 재수집이나 Supplier Hub 전송은 이 동작에 포함되지 않는다.
