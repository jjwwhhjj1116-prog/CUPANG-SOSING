# 카테고리 선택 시 기존 견적서 양식 유지

## 문제와 변경

상품 추가 화면의 카테고리 목록을 불러온 뒤 다른 화면에서 같은 분류의 견적서 설정을 저장하면, 이전 목록에는 연결된 설정이 보이지 않는다. 이 상태에서 관찰 목록의 최종 카테고리를 선택하면 기존 설정을 확인하지 않고 빈 프로필을 새로 만들었다. 선택 코드가 같아도 이미 연결한 Excel 양식과 열 매핑을 사용하지 못하는 원인이었다.

`CategoryPicker`는 새 빈 프로필을 만들기 전에 현재 계정의 저장 목록을 모든 페이지에서 다시 읽는다. 선택한 코드와 전체 카테고리 경로가 정확히 일치하는 설정이 하나면 그 설정의 최신 버전·양식·열 매핑을 그대로 URL 수집 단계에 전달한다. 마지막 분류 이름만으로 다른 경로나 코드의 양식을 가져오지 않는다.

같은 코드·전체 경로에 설정이 여러 개면 갱신된 목록을 표시하고 사용할 설정을 선택하게 한다. 임의로 첫 양식을 선택하거나 새 빈 프로필을 만들지 않는다. 일치하는 설정이 없을 때만 기존의 요청 번호를 유지하는 생성 경로를 사용한다. 목록 조회 실패·잘못된 페이지 위치·취소·잘못된 저장 버전은 새 설정 생성으로 이어지지 않는다.

기존 저장 설정을 직접 선택했을 때 코드·경로·버전의 변경을 확인하는 동작은 유지한다. 변경된 양식은 화면에서 확인한 뒤 선택할 수 있다. 저장한 카테고리 설정과 기존 작업 상품을 조회 과정에서 수정하지 않는다.

이 변경은 이미 연결된 견적서 양식을 유지하는 수정이다. 미확보 카테고리의 Supplier Hub 공식 Excel이나 쿠플러스 기본값을 새로 확보한 것은 아니다. 코드·경로 일치는 정확한 양식 선택의 조건이며, 쿠플러스와 전체 공식 항목·기본값이 일치한다는 증거를 대신하지 않는다.

## 검증 범위

새 UI 회귀 두 개는 수정 전 실패했다. 최신 양식을 재사용해야 하는 시험에서 `blank` 설정을 선택했고, 같은 분류에 양식이 여러 개 있는 시험에서도 빈 설정을 생성했다. 수정 후 관련 카테고리·UI 검사 27개가 통과했다. 전체 경로·코드 일치, 서로 다른 설정 유지, 페이지를 끝까지 읽은 뒤 선택, 불완전 조회·잘못된 버전·취소 시 생성하지 않음도 검사한다.

`tests/category-template-intake-linkage.test.mjs`는 실제 카테고리 선택 컴포넌트·카탈로그·목록 API·수집 API·견적 API·Excel 생성과 임시 SQLite를 연결한다. 와이홉 `A01464742`, 유앤채 `A01526306` 각각에서 다음을 확인했다.

1. 초기 목록이 빈 선택 화면에서 `80719`를 선택하면 현재 소유자의 저장 양식·열 매핑을 가져온다. 같은 분류의 다른 소유자 설정을 가져오지 않고 새 프로필도 생성하지 않는다.
2. 선택한 프로필과 분류 코드가 기록된 1688 원문 수집, 옵션 6개 저장, SEO 초안, 단계 입력과 견적서까지 유지된다.
3. 수정한 상품명·재질, 옵션 하나의 명시적 재질 공란이 실제 생성한 Excel의 6개 행까지 유지된다.
4. 견적 ZIP과 실제 전송 준비 컴포넌트를 거쳐 로컬로 포착한 전송 데이터에 회사·프로필·카테고리·포함 옵션 수가 유지된다.
5. 저장 프로필의 원본 DB 행은 전 과정에서 같고, 실제 Hub 영수증이 없으므로 최종 상품 상태는 `미전송`이다.

인증·AI 응답·이미지 바이트·Excel 양식·최종 Hub 전송은 격리된 시험 자료다. 지정 상품 `813724060928`의 기록된 공개 원문을 사용하며, `80719`는 관찰한 폼 연결의 시험 계약이지 해당 선글라스의 판매 분류가 아니다. 선택형 수납 재질은 시험에서 명시적으로 공란으로 지워 필드 검사를 충족했다. 초기 통합 시험은 VM의 `structuredClone` 누락과 이 선택형 시험 입력을 보정한 뒤 통과했다. 실제 Chrome에서 수집하거나 실계정 Hub에 등록한 시험은 아니다.

추가 회귀 8개 포함 전체 **1,497/1,497**, TypeScript, 변경 파일 ESLint 오류/경고 0을 통과했다. 전체 저장소 lint 또는 모든 카테고리의 공식 기본값 대조 완료를 주장하지 않는다.

## 운영 반영

기존 앱 https://sourceflow.jjwwhhjj1116.workers.dev 에 배포했다. Worker 버전은 `4d2298d1-1bb3-4247-bf88-3a4b0b000132`다. 앱 새로고침으로 적용한다. 운영 빌드·산출물·diff 검사도 통과했다.

확장 0.2.29는 변경하지 않았고 빌드에서 30개 파일/366,181바이트/SHA-256 `80a1d38d37bcd65b6b6d8e83e7c268d289b95320f00c91d0ae80147b21684444`를 다시 확인했다. DB 마이그레이션·비밀 설정·공개 이미지 Worker·유료 자원 변경은 없다.

배포 후 앱·확장 ZIP·수집 API의 익명 HTTP 302 Access 보호를 확인했다. 인증한 운영 화면·다운로드 바이트·실제 Hub 접수 성공 검사와는 다르다. 기존 Chrome 제어 바인딩의 탭 목록은 `[]`였으며 이를 사이트 차단이나 로그아웃으로 해석하지 않았다. 새 Chrome 창·프로필과 기존 작업 상품을 조작하지 않았고 로그인·승인을 다시 요청하지 않았다.

## 남은 실검증

지정 Chrome에서 실제 URL→1~7단계 초안, 전체 카테고리의 쿠플러스 기본값·공식 양식 대조, 운영 이미지 번역·법적 서류 첨부, 두 회사의 실제 견적서 접수·SKU 확인이 남아 있다. 이번 변경 완료를 전체 시스템 완료로 보고하지 않는다.
