# Step 712 — 저장 라벨 결과 판정의 실제 API 검증

## 범위

`tests/product-label-result-api.test.mjs`에서 새 `readCurrentProductLabelResult()`를 실제 라벨·견적·파일·업로드·첨부 route와 격리된 SQLite/R2에 연결했다. 유앤채 `A01526306`, 와이홉 `A01464742` 두 회사 각각 같은 시나리오를 실행했다. 이 작업자는 앱 코드를 변경하지 않았다.

제품·카테고리·PNG·인증은 합성 fixture다. 이미지 렌더링 픽셀이나 외부 사이트의 실제 접수는 이 테스트의 검증 대상이 아니다.

## 검증한 연결

1. 실제 PNG 업로드·상품 풀 연결·최종 견적 참조 저장 뒤 현재 라벨 결과를 판정한다. 반환 키가 실제 선택 파일이고, 인증된 생성 proof와 `filtered` 계획을 가진다.
2. 문구를 바꾸지 않고 재작성 POST로 세대를 올리면 이전 파일은 보존되며 결과는 `stale`이 된다. 새 PNG를 생성·첨부하면 현재 세대의 저장 결과가 된다.
3. 수동 파일, 복수 참조, 빈 참조를 각각 `manual`, `ambiguous`, `missing`으로 분리한다. 자동 파일 선택이나 저장은 없다.
4. 현재 상품 풀에서 제외한 생성 파일도 업로드 receipt는 존재하지만 완료 결과로 사용하지 않는다. 현재 소유자 파일이 없을 때 다른 소유자 네임스페이스의 동일 업로드 ID 파일로 대체하지 않는다. 이 두 경우는 `unconfirmed`다.
5. R2 HEAD 오류와 손상된 생성 세대 메타데이터는 실제 파일 API의 503이며 판정 helper가 오류를 전파한다. 이를 미완료나 재생성 허가로 바꾸지 않는다.
6. 실제 공통 참조 상속은 같은 현재 계획·세대일 때 완료로 인정한다. 옵션에 같은 공통 파일을 직접 선택한 경우는 공통 상속으로 추정하지 않는다.
7. 다른 소유자의 상품과 다른 회사 컨텍스트는 거절한다.
8. 파일 proof 응답 뒤 상품 원천 시각을 바꾸면 마지막 참조 재조회에서 경합을 거절한다. 이후 같은 계획·세대의 안정된 조회는 정상 결과를 유지한다. 라벨 내용과 무관한 시각 변화만으로 같은 파일을 재생성하지 않는다.

각 정상 판정 전후에 모든 업무 테이블과 파일 바이트의 동일성을 확인하고 판정 transport가 GET만 실행했음을 검사했다. 의도한 동시성 주입에서는 그 주입 변경만 남는지도 확인했다.
