# Step 883 — 원래 문서 읽기 오류와 이미지 자동 작업

2026-10-31 KST. 원래 886 상품·요청·문서 2347603의 파일·본문 재전송 및 새 문서 생성은 금지된 상태다.

## 읽기 오류의 실제 경계

- 실제 웹 문구는 `ADAPTER_FAILURE`의 일반 오류이며, 웹의 180초 ACK 제한 문구와 다르다. 기존 로그만으로 어느 일반 예외가 원인인지 확정할 수 없다.
- 원래 상품의 `legal-documents` GET을 현재 로그인 Chrome에서 읽어 revision 12, native 양식 있음, native issues 0, targets 4, 서류 해당 없음·files 0을 확인했다. 별도의 `catalog-context` GET도 원래 유앤채 회사와 일치했다. 두 GET은 읽기 전용이며 이 응답만으로 원격 Hub 본문의 전체 일치를 주장하지 않는다.
- 원래 Chrome 연결 ID 6이 사라져, 새 인벤토리의 같은 provider session `ca7efe32…` 및 같은 원래 탭 식별자로 ID 7을 확인했다. 다른 프로필의 작업 탭은 사용하지 않았다. 원래 4개 검수 탭은 보존한다.

## 수정한 결함

- 감사 스키마의 catalog → legal documents → catalog가 하나의 30초 제한을 공유했다. 각 GET의 fetch와 body 소비를 요청별 30초로 분리했다. 취소를 무시하는 요청도 제한에서 끝나며, 늦게 완료해도 다음 GET을 시작하지 않는다.
- 스키마 HTTP·JSON·응답·시간 초과와 Chrome 실행·결과 검증의 실패는 고정된 단계와 코드로 분류한다. 원문 예외나 비밀 값은 표시하지 않는다.
- 웹 감사 UI도 읽기 실패를 전송 결과 미확정과 구분해 해당 단계·코드를 보여준다. 원래 요청·회사·원문·체크포인트·60초 보고서 유효성 검증은 유지한다.
- 감사는 계속 `canResume=false`, `canDelete=false`이며 세션 채택·자동 재시도·저장·파일 삭제·등록을 허용하지 않는다. 일반 신규 문서의 저장·전송 경로는 변경하지 않았다.

## 검사

- 확장 관련 127개 검사 통과: 실제 직렬화 함수, 요청별 11초×3=33초 성공, fetch/body의 취소 무시·늦은 완료, source drift, 코드 분류, 체크포인트/쓰기 부재.
- 웹 관련 137개 검사 통과: typed 오류 보존·raw 오류 비노출, 기존 180초 제한·취소·재시도 부재, preview/대조/대조 후 원본 확인 단계, 세션·등록 권한 채택 부재.
- 두 변경의 타입·ESLint·diff 검사 통과. 독립 검토에서 추가 P1/P2 결함 없음.

## 적용 상태

- 확장 2.1.69, 113파일, ZIP 1,657,590 bytes, SHA-256 `cb674982624f524fd48cb02790c6aee62da96690307b41231aaa8ff8ce58f6c9`.
- 실제 사용 폴더의 2.1.68을 백업하고 갱신했다. 113파일 해시와 권한·호스트 목록이 일치한다. Chrome 적용은 사용자 새로고침 확인 대기다.
- 원격 문서의 상세 대조·실제 접수는 아직 확인하지 못했다. Step 881 Preview의 저장 부작용 가능성은 미확정 상태이며, 이번 읽기 수정으로 이를 없었던 일로 취급하지 않는다.

## 2.1.69 실제 결과로 확인한 주원인과 후속 수정

사용자가 2.1.69 적용을 확인했다. 원래 YOOFAM 탭을 F5 하고 저장 견적·원래 요청을 읽기로 복구한 뒤 감사 1회를 실행했다. 이번에는 정확히 `UNEXPECTED_LEGAL_AUDIT_SCHEMA_EXECUTION`에 해당하는 문구가 표시됐다. HTTP 조회 시간이 아니라 스키마 함수의 Chrome 실행 자체가 거절된 경계임을 확인했다.

manifest에는 YOOFAM이 `content_scripts.matches`에만 있고 프로그램 방식 주입용 `host_permissions`에는 없다. 기존 네이티브 원본 읽기는 이미 콘텐츠 스크립트 메시지를 사용하고 있었으나, 추가된 스키마 감사만 앱 탭의 `executeScript`를 호출했다. 이것이 실제 경로와 권한 계약이 맞지 않았던 원인이다.

- 스키마 감사를 기존 manifest 설치 콘텐츠 스크립트의 전용 메시지로 전달하도록 교정했다. 정확한 자체 확장 sender, 입력 키, 최상위 프레임, 앱 탭·창·출처의 전후 검증을 유지한다.
- 동일한 기존 GET 3개만 사용한다. 주입 재시도나 새 호스트 권한·외부 주소·Hub 쓰기는 추가하지 않는다.
- 실제 콘텐츠 리스너와 스키마 함수, 앱 `executeScript`가 거절되는 fixture를 연결한 102개 검사와 타입·ESLint·독립 검토가 통과했다.
- 확장 2.1.70: 113파일, ZIP 1,664,313 bytes, SHA-256 `4299ca5d47edca26a09bc2bb4b7d321421689dd344986ca0bbfe52286aeecb29`. 실제 2.1.69 폴더를 별도로 백업하고 갱신했다. 권한 목록은 동일하며 사용자 적용 확인 대기다.

## 이미지 자동 작업

구현·검토를 마쳤다. 명시적 no-foreign-text 결정과 현재 불변 원본 SHA·회원·회사·모델·계약 버전이 결속된 새 서버 완료 기록만 사용한다. 구형 빈 결과, unreadable, 미확정 요청은 완료 처리하지 않는다. 기존 요청 복구와 미확정 추론 방지 계약을 보존한다.

122개 focused 검사 및 양 회사의 전체 1~7단계 통합 5개 검사 통과. 현재 원본 유지 검증이 맞으면 3~5에서 추가 추론·렌더·이미지 저장 없이 완료되어 표시사항·견적서로 이어진다. 원본 없음·증거 불일치·읽기 실패는 뒤 단계 자동 진행을 막는다. 기존 실행 중 상태와 더 최근의 실패를 무시하지 않는다. 상세 설계와 실제 SQLite/목록 통합 검수는 [별도 기록](./step883-image-no-text-proof.md)에 있다.

## 배포 대기 사항

운영 빌드는 통과했다. 새 migration 0038은 검증 기록용 표만 생성하며 기존 상품 행을 변경하지 않는다. 원격 적용은 기존 Cloudflare OAuth의 오류 10000으로 실패했고, 같은 6개 기존 권한만 요청하는 갱신 화면을 열었다. Authorize에 개인정보처리방침 동의가 포함되어 있어 실행 시점 확인을 요청했다. 아직 동의·갱신 완료 및 migration·Worker 배포는 확인하지 못했다. 새 결제나 요금제 변경은 없다.

최종 적용: 사용자가 2.1.70 새로고침과 동일 권한·개인정보처리방침 동의를 승인했다. 첫 OAuth 요청은 2분 제한으로 끝나 새 동일 요청으로 갱신했고, 공식 CLI에서 성공을 확인했다. 인증 후 안내 도메인의 화면 읽기는 도구가 거절했으나 그 내용을 읽을 필요 없이 CLI 결과로 확인을 마쳤다. 해당 거절을 다른 도구로 우회하지 않았다.

migration 0038 적용과 Worker `58ad3706-231c-4e5f-a10a-310204c5d1e4` 배포 성공. 코드 커밋 `79ccc5a`를 main에 올렸다. 보존 대상 35테이블·47행은 `39f1f5b9ff48173e6d68b0e8d9689aac8eb587f2fb469a0ed6b2984913a3455d`로 이전과 동일하다. 원격 Supplier Hub 본문·접수 증거와 구분한다. 2.1.70으로 원래 웹을 F5한 후 원래 요청의 읽기 검증을 이어가는 중이다.

## 2.1.70 실제 조회와 공식 로그인 만료 확인

- 같은 원래 요청을 읽기로 복구해 감사를 실행했다. 스키마 권한 오류를 지나 `UNEXPECTED_LEGAL_AUDIT_READ`, `draft-list / http-redirect`까지 진행했다. 파일·본문 쓰기나 새 생성은 실행하지 않았다.
- 별도의 빈 SR StartPage에서 소스로 확인한 안전한 헤더의 중간저장 목록 열기만 실행했다. 회사명은 남아 있었지만 목록은 상품명·카테고리가 없는 2,095행을 표시했다. 이 표시는 유효한 저장 목록 또는 로그인 성공의 근거로 사용하지 않는다.
- 그 빈 탭에서 공식 `홈` 링크를 누르자 `xauth.coupang.com`의 ID·비밀번호 입력 로그인 화면으로 이동했다. 이 직접 관찰로 이번 세션 만료를 확인하고 사용자에게 별도 탭의 로그인만 요청했다. 원래 문서·예약 읽기·YOOFAM 탭은 보존했다. 증거: `outputs/step883-hub-session-expired.png`.
- 공식 Axios GET과 감사 GET의 경로·방식은 일치한다. `credentials:include`를 제거하거나 redirect를 자동 추종하는 변경은 하지 않는다. 일반 `http-redirect`를 무조건 인증 오류로 승격하지도 않는다. 현재 UI가 원래 단계·코드를 유지하며 공식 로그인 확인 링크를 제공한다.
- 로그인 완료 뒤 같은 원래 문서의 읽기 대조를 재개한다. 실제 접수 및 Preview 사고의 본문 영향 확인은 여전히 미완료다.
