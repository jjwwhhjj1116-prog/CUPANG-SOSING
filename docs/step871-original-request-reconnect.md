# 원래 저장 문서의 웹 요청 연결 복구

2026-10-30. 기존 상품·요청·문서번호를 유지하며, 새 문서 생성과 파일·본문 재전송 없이 이어가는 복구 경로다.

## 실제 확인한 원인

원래 886 상품 `e2f8037c-294e-45a8-b06d-58cc5909683c`의 웹 전송 요청 기록이 없다는 결과를 운영 UI에서 확인했다. 원래 요청은 `f29491bd-1882-456a-8a63-eec8586db6c6`, 문서는 `2347603`이다. 기존 화면은 웹 기록이 없으면 새 preview UUID를 만들었으며, 같은 본문에 남아 있는 확장 체크포인트의 원래 UUID와 달라 CHECKPOINT_MODE가 발생할 수 있었다. preview 오류는 새 문서 생성 성공을 뜻하지 않는다.

웹 요청 진단은 없음·읽기 실패·동일 요청·다른 요청을 구분한다. 인증된 회원·회사·상품 범위의 기존 parser를 사용하며 조회 전후 회원·회사를 확인한다. 본문·해시·탭 식별값을 진단 결과에 노출하지 않는다. 입력 변경·회원 전환·취소 시 결과를 폐기한다. 구버전 확장에서도 웹 진단은 볼 수 있지만 원래 확장 체크포인트 조회에는 지원 버전이 필요하다.

## 추가한 재연결 경로

전송 자료 안의 접힌 **원래 요청 연결 복구**에서 원래 UUID와 문서번호를 명시한다. 정상 신규 등록과 원래 웹 기록이 남아 있는 기존 재개 흐름은 유지한다.

1. 현재 서버의 전체 견적 자료를 읽고, 동일 회원·회사·상품의 웹 예약이 없으며 반려 기록이 없는지 확인한다.
2. 확장 보관함의 실제 원래 체크포인트를 조회한다. 정확한 요청·문서·lane이며 저장 완료된 `updated` 또는 `validated`, 미제출, `draftOnly:true`, 기존 제출 lifecycle 미진입인 경우만 받는다. 생성 전·생성 직후·미확정·반려·제출 대기 상태는 이 경로에서 예약하지 않는다.
3. 현재 전체 견적 자료와 원래 UUID로 기존 native preview를 실행한다. 보관 보고서의 해시로 session을 조립하지 않는다. 기존 preview가 현재 원문·회원·회사·본문·옵션·파일 연결과 private 체크포인트를 직접 검증한다.
4. 체크포인트를 다시 조회해 상태·sequence·source·본문·옵션·브라우저 identity가 바뀌지 않았는지 확인한다. 같은 문서에 `recoverDraft` 읽기를 실행한 뒤 결과를 다시 대조한다.
5. 검증된 원래 UUID만 기존 Web Locks/CAS를 통해 웹 예약에 보관한다. 새 Hub 문서·파일·본문·검증·동의·제출 요청은 이 함수에서 호출하지 않는다. 기존 readback은 이미 검증된 로컬 확장 체크포인트를 `updated`에서 `validated`로 승격할 수 있다.
6. 저장 완료 상태면 기존 단계 검증으로, 검증 완료 상태면 기존 등록전송·현재 약관 확인·제출·접수 결과 조회 흐름으로 연결한다. 복구 버튼 자체는 다음 단계를 자동 실행하지 않는다.

모든 비동기 경계에서 현재 서버 견적 전체와 화면 epoch를 확인한다. 예약 저장 후 마지막 읽기가 실패하더라도 원래 예약을 지우지 않는다. 같은 창에서는 storage 이벤트가 발생하지 않으므로 실패 처리에서 예약을 다시 읽어 원본 편집·닫기 잠금에 즉시 반영한다. 반환되지 않은 session이나 문서 상태는 적용하지 않는다.

## 검증 범위

원래 ID·회사·본문·옵션·source·브라우저 identity 불일치, 미확정/생성/제출 상태, 중간 변경·취소·다른 예약 경쟁과 예약 후 실패를 검사했다. 재연결 helper의 synthetic native 경계와 실제 웹 pending/Web Locks 함수 검사를 사용한다. 이 검사와 브라우저의 실제 접수 결과는 구분한다.

최종 고유10개 테스트 파일196개를 통과했다. 초기 분리 실행195개 중 transport UI86개를 마지막 수정 뒤87개 통과 결과로 교체한 수이며 중복 실행을 더하지 않았다. TypeScript·변경4개 파일 ESLint·최종 분리 빌드와9개 릴리스 파일SHA 대조를 통과했다. 독립 검토에서 예약 후 실패 시 잠금이 풀리는 P2를 찾아 수정·회귀 검증했으며 남은 P1/P2는 없다. 최종 Worker `4598d490-d71d-4619-9795-fe432af90be7` 배포.

원래 범위 D1의35개 테이블47행 hash는 직전869 검수와 같은 `39f1f5b9ff48173e6d68b0e8d9689aac8eb587f2fb469a0ed6b2984913a3455d`다. 이번 개발에서 기존 상품·옵션·견적·파일 참조·회원 설정을 바꾸지 않았다. 인증 세션 자체는 이 비교의 대상이 아니다.

운영 화면에서는 원래 웹 기록 부재와 Chrome 확장 **2.1.59**의 체크포인트 조회 미지원을 확인했다. 준비된 확장은 **2.1.61**이며 이번 웹 수정은 확장 버전·권한·호스트를 변경하지 않는다. 실제 복구·단계 검증·문서2347603의 접수 완료는 아직 검증 전이다. 새로고침 요청은 사용자 응답 대기다.

배포 후 기존 Cloudflare 인증과 승인된 유앤채 계정의 로그인을 복구했다. 정확한 등록번호261024001001의 저장된3옵션 견적·첨부 자료를 읽고 새 복구 UI에 원래 UUID/문서번호를 입력했다. 실제 복구 버튼1회는 설치 확장2.1.59 미지원 사전검사에서 종료됐다. 새 문서·파일·본문·단계 검증·제출 호출은 진행되지 않았으며, 복구 입력과 기존 Hub 탭을 보존했다. 화면은 로컬 `outputs/step871-live-original-reconnect.png`에 보관했다.

Couplus의 보관 REA 근거 `ev_17ed0cebd00b285e0bc489221547e437d2b3f69d9b636a813eb942a0a2a3a49a`에서 중간저장 문서 선택→단계 이동→동의→제출→완료 문구 대기를 정적으로 재확인했다. YOOFAM은 완료 문구만으로 접수로 표시하지 않고 원래 문서/qvt 결과를 확인한다. 정적 비교를 이번 실제 접수 성공으로 보고하지 않는다.
