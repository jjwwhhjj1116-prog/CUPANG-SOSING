# Supplier Hub 견적서별 결과 페이지 대조

기존 등록전송 후 조회는 정확한 견적서 ID를 검색해도 현재 표의 첫 페이지밖에 읽지 않았다. 옵션이 다음 페이지에 나뉘면 일부 SKU만 표시하고 계속 기다리는 문제가 있었다.

## 구현 범위

- 앱의 저장된 검증 완료 ID, 자료 지문·카테고리·회사·전송 옵션 수에 연결된 같은 Chrome 창의 전용 상태 조회 탭만 사용한다. 각 페이지 읽기 전후 현재 회사코드와 저장 검증 결과를 다시 대조한다.
- 검색 후 첫 페이지부터 시작한다. 페이지 영역에 표시된 현재 숫자와 정확히 다음 번호의 버튼, 또는 `다음`/`다음 페이지`/`Next`/`Next page` 제어를 이용한다. 중복·숨겨진·다른 출처/화면으로 이동하는 제어, 페이지 건너뛰기와 검색 필터 변경을 거부한다. 숨겨진 API, 페이지 내부 애플리케이션 상태와 쿠키를 읽지 않는다.
- 페이지 클릭 후 결과 표 변경과 다음 번호를 모두 확인한다. 350ms 동안 갱신이 가라앉은 뒤 판독하며 8초 안에 확인하지 못하면 실패한다. 회사 메뉴가 클릭으로 닫힐 때는 대기 중 표시 회사명을 대조하고, 결과를 받자마자 회사 메뉴의 전체 코드를 다시 확인한다.
- 실제 일치 행을 순서대로 모으고 옵션 수 초과·고유 SKU 중복을 거부한다. SKU가 없는 같은 모양의 행을 합치거나 제외하지 않는다. 전체 SKU는 해당 셀의 보이는 복사 버튼 값으로 확인하며 표시값이 모순되면 거부한다.
- 조회는 최대 60초/200페이지이며 앱 응답 기한은 120초다. `queried-pages`에는 실제 `pagesRead`와 `hasMore`를 기록한다. 마지막 페이지 확인 `false`, 다음 페이지 존재 `true`, 제어 불명확 `null`을 구분한다. 페이지 영역 자체가 불명확하면 `visible-page` 결과로 한정한다. 조회 중 실패한 부분 결과는 저장하지 않는다.
- 전송 옵션 수와 같은 수의 SKU를 읽어도 알려진 다음 페이지가 남으면 발급 확인을 끝내지 않는다. `registered:false`를 유지한다. 수동 결과 조회도 읽기 전후 서버의 현재 초안을 대조하여 조회 도중 수정한 이전 견적서 결과를 표시하지 않는다.

## 근거와 한계

9열 상품 결과 표, 견적서 ID 검색 양식·재설정, 전체 견적서 ID 복사 버튼과 회사 메뉴는 기존 Hub 관찰 근거를 사용했다. 페이지 제어와 SKU 복사 버튼 변형은 이번 합성 DOM 계약 시험이다. 실제 Hub의 페이지 마크업을 새로 관찰하거나 실계정 견적서를 전송한 결과가 아니다. 해석할 수 없는 페이지 제어를 전체 결과로 추정하지 않는다.

실계정 여러 페이지 이동과 모든 옵션 최종 등록, 모든 카테고리의 Couplus 기본값·공식 양식 일치, 성공 후 추가 등록 조작 유무, 운영 AI와 이미지 번역, 공개 상세 HTML·법적 서류 첨부 검증은 남아 있다. 기존 Couplus 작업 상품과 Hub 견적서는 수정하지 않았다.
