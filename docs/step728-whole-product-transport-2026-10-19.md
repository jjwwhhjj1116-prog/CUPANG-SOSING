# Step728 — 전체 옵션 문서 전송과 접수 이력 연결

기준 `a7fca1cdd1be9e8b310c6f47b23435e9dcc9d3f3`, 2026-10-19. 기존 작업 상품·회원 설정·원래 Couplus/Supplier Hub 탭은 변경하지 않았다. 현재 원본 비교 근거는 [REA 단계 계약](step727-rea-stage-contract-2026-10-19.md)과 Step724–726의 shipped extension·전체 옵션 문서 분석이다. 이번에 원본의 비공개 1688 공급자를 복구하거나 실제 등록을 완료했다는 의미가 아니다.

원본에서 확인한 구조대로 포함 옵션 전체를 같은 순서의 `jsonDocument` 배열로 묶고, 문서 생성 1회와 같은 문서 ID의 갱신·검증·제출 경계를 구현했다. 각 옵션을 서로 다른 문서로 분할하는 기존 단일 옵션 계약은 별도로 유지한다. 전체 문서 확인 화면에서 새 전송 미리보기로 연결하며, 현재 회원·회사·카테고리·옵션 순서·수동 공란·전체 본문을 전후에 다시 조회한다. queryless 카테고리의 `requestedProfileId:null`을 캡처된 프로필 ID로 바꾸지 않는다.

확장의 새 `PRODUCT_DOCUMENT` 경로는 120초 유효한 불변 패킷을 검사한다. 최초 미리보기와 시작은 만료 요청을 거절하고, 이후 같은 요청의 복구는 정확한 기존 체크포인트가 있을 때만 허용한다. 두 계약은 동일한 수신 엔진·전용 탭 소유권·단계별 약관 확인·본문 읽기 복구 코드를 공유한다. 모든 옵션의 알려진 동의 플래그는 제출 시점의 실제 확인과 분리한다. 원래 사용자의 작업 탭이나 기존 Hub 초안을 재사용하지 않는다.

독립 검수에서 세 가지 결함을 찾아 회귀 검사를 추가했다. 첫째, 옵션명·순서·카테고리·프로필을 바꿔 미확정 요청의 중복 방지를 피할 수 있었다. 문서 해시는 전체 내용을 계속 묶고, 생성 중복 방지 범위는 회원·회사·상품에 고정했다. 둘째, 복구 결과의 진단 메타데이터가 엄격한 접수 저장 계약과 충돌했다. 원래 응답을 유지하며 문서화된 진단 정보만 복사본에서 분리한다. 셋째, 전체 상품 문서의 반려 결과를 뒤이은 조회가 다른 상태로 덮어쓰지 못하도록 수신기와 화면에서 보호한다.

새 접수 기록은 기존 native JSON 테이블을 사용한다. SQL 스키마·DB 마이그레이션 추가는 없다. 문서 하나에 실제 `docId`, `qvtRequestId`, 불변 옵션 목록과 본문 해시를 저장한다. 가짜 단일 `optionId`나 옵션별 중복 접수 기록을 만들지 않는다. 기존 단일 옵션 v1 이력과 전체 상품 이력을 함께 엄격하게 검증하며, 모르는 형식이나 불완전한 이력은 삭제·재전송을 허용하는 근거가 되지 않는다. `FINISHED` 파일 처리 결과만으로 개별 SKU가 등록됐다고 표시하지 않는다.

고정 소스 1,338개를 기준으로 관련 46개 테스트 파일의 **797/797** 검사가 통과했고 검사 중 소스 변경은 없었다. 이후 마지막 검수에서 정상 반려 이력은 재제안을 허용하면서 처리 중·완료 문서의 다른 요청은 계속 차단하도록 보완했다. 상태·회사·문서·해시 연결이 어긋난 위조 반려 기록은 허용하지 않는다. 화면에 수십 번 반복되던 검토 안내는 중복을 제거해 접힌 목록으로 정리했고 오류 항목은 그대로 표시한다. 이 최종 변경까지 별도 `closure` 동결 검사 **797/797**로 다시 검증했다.
