# Step715 — URL 원문 저장 후 초안 진행 복구

기준 커밋은 `81ba0a32fda5554873380f7b3a2f3ae6f86e8e70`이다. 카테고리와 URL 입력 후 원문을 실제로 저장했는데도 응답 유실 때문에 편집 가능한 초안에 도달하지 못하는 문제, 검증한 SKU까지 부가 상세 요청의 장애로 버리는 문제를 수정했다.

## 동작 변경

`/collect` 또는 `/browser-capture`의 전송·응답 본문이 끊기거나 불확실한 서버 오류가 발생하면 같은 요청의 `/result`를 GET 한 번 조회한다. 소유자에 결속된 job·offer·정확한 source URL·유효한 저장 시각을 가진 receipt가 있을 때만 기존 import→SEO/옵션→이미지 초안 흐름을 이어간다. POST를 자동 반복하지 않는다. 명확한 거절, 정상 JSON의 잘못된 원문, 저장본 부재, 취소는 성공으로 바꾸지 않는다. 확인된 receipt 이후 기존 원문 보완 조건은 그대로 유지한다.

모바일 상품 본문과 SKU·위안 단가·MOQ가 검증된 뒤 부가 상세 요청만 전송 실패하거나 정체되면 서버는 검증된 부분 원문을 보존한다. 이 부가 요청에 자체 기본 5초 예산을 적용했고, 이미지·상세 설명의 누락 검토는 계속 남긴다. 권한 오류, redirect, 잘못된 상품 식별·가격·인코딩·과대 본문·상위 취소는 계속 거절한다. raw Chrome capture의 HTTP 상태 계약을 늘리거나 없는 HTTP 504를 만들지 않는다. 별도 source provider나 유료 API를 추가하지 않았다.

공유 parser를 포함한 확장 0.2.77과 다운로드 링크를 준비했다. 기존 0.2.76 ZIP은 유지한다. manifest 권한이나 Supplier Hub 실전송 gate는 변경하지 않는다. 사용자의 설치 확장 버전은 이번에 재조회·업데이트하지 않았으며 서버 복구 변경은 앱 배포로 적용한다.

## 원본 분석

REA로 보관 원본의 `handleAddProduct`, extension 응답, `createProductObject`, `runInitialProcessing`을 대조했다. 일반 URL 입력은 서버 상품 조회 응답을 받아 초안을 생성한다. private backend의 실제 데이터 공급처, cache, 공식 API 사용 여부와 처리 속도는 이 클라이언트만으로 확인되지 않는다. 이번 ACK 복구는 자체 durable receipt를 이용한 수정이며 원본에 같은 내부 복구가 있다는 주장이 아니다. 세부 범위·digest·REA evidence는 [원본 대조](step715-intake-parity-audit.md), [상세 원문 보완](step715-intake-gap-audit.md)에 기록했다.

## 전체 흐름 검수

새 통합 검사는 실제 자체 route·SQLite·원문 importer·SEO/옵션·상품 내용 수정·7단계 견적 수정·공식 XLSX·Single projection을 실행한다. 양사 각각 응답 유실 세 종류와 부가 상세 전송 실패를 사용한다. 모든 외부 상품·이미지·모델 요청은 보관 원문 또는 합성 응답으로 대체한다.

각 경우에는 원문 POST 한 번, 같은 job 복구 GET 한 번 후 상품 초안 하나가 생성된다. 원문의 6개 SKU·단가·MOQ, 카테고리 69900과 profile/path, 다섯 견적 섹션을 검사한다. 사용자가 제목·한국어 옵션명·브랜드·공란을 수정하고 한 옵션을 제외하면 공식 XLSX와 Single 문서에 포함 옵션 다섯 개만 반영된다. 원문 receipt와 별도의 기존 작업 보호용 합성 상품·편집값·등록번호·견적값은 변하지 않는다. 상세 누락은 완료로 표시하지 않는다.

69900 Single·공식 Excel 원본은 유앤채의 보관 자료다. 와이홉 검사는 이 계약을 합성 재사용하며 와이홉의 실제 원격 양식 재검증이나 두 회원의 실제 로그인 증거가 아니다. 통과 수는 focused 재실행과 합산하지 않고 최종 고유 파일 실행 결과만 집계한다. 이전 source repair 테스트의 공통 제목 단독 가정 두 건은 HEAD에서도 같은 실패를 확인한 뒤 현재 옵션별 제목·수동 견적 우선순위 검사를 강화했다. 첫 25파일 실행은 362개 중 이와 같은 오래된 제목 가정 6개만 실패했다. 해당 public collection 테스트도 HEAD에서 같은 실패를 확인했다. 제목 이후 가려진 고시 재질 가정 역시 초기 기본값과 표시사항 편집이 독립이라는 현재 계약에 맞춰, 기본값 보존과 명시적인 수동 견적값 반영을 각각 검사하도록 강화했다. 실패·baseline 로그는 삭제하지 않았다.

## 최종 검사

고유 25파일 **362/362 통과**, 실패·취소·건너뜀·todo 0, 124.86초다. 신규 사례는 ACK 복구 52개·부가 상세 기한 10개·양사 통합 8개이며 focused 반복 실행 수를 다시 더하지 않았다. 검사 전후 앱·DB·테스트·설정 등 1,290개 파일의 SHA가 일치하고 추가·삭제가 없다. 전역 타입, 앱·DB 및 변경 테스트 lint, 44테이블·17인덱스·29모듈 스키마 검사, 운영 빌드가 통과했다. 수집·복구·확장 ZIP·세 통합 테스트에 대한 독립 읽기 검토의 미해결 지적은 없다.

Ignored `outputs/step715-final-verifier.mjs`는 최종 TAP·소스 고정·초기 실패 로그·원본 exact slice·REA evidence·독립 검토·확장 ZIP·live gate·빌드·배포 식별자를 대조한다. release-inputs와 final-validation은 검증 자료이며 운영 상품 데이터가 아니다. 전체 저장소 테스트나 실제 외부 수집·접수·픽셀 동일성의 증거로 표현하지 않는다.

기존 무료 Worker에 버전 `f7e1130a-c94d-4907-a777-92826029c090`을 배포했고 최종 verifier도 통과했다. 새 DB migration·유료 리소스·provider·OAuth/R2 권한은 없다. 준비한 확장 ZIP SHA-256은 `cd1433734850ed2cfae2ba7a58813714d90bc7cb54bfdd1ba9c94a20d6875a13`이다.

## 실제 접속과 남은 검증

사용자가 열어둔 Chrome 4에서 Supplier Hub의 유앤채 로그인과 새 개별 상품 등록 빈 화면을 확인했다. 원래 등록 목록의 건을 열거나 수정하지 않았고, 새 화면에 값을 입력·저장·등록하지 않았다. 앱의 상품 추가 팝업은 열기·닫기만 했으며 복원된 기존 로컬 입력 행을 변경하거나 수집하지 않았다. 빈 양식 AX 기록은 ignored `outputs/step715-live-hub-empty-form.txt`에 보관했다. 화면 캡처는 도구의 CDP 시간 초과로 저장되지 않아 픽셀 검증으로 주장하지 않는다.

이전 자동 검토가 거절한 1688 도메인·상품 URL을 다른 도구·앱·확장·CLI로 우회해 다시 요청하지 않았다. 이 제한은 자체 collector가 일반적으로 불가능하다는 증거가 아니다. 허용된 실제 신규 상품의 전체 원문 수집, 전 카테고리의 공식 양식·기본값 대조, 새 Hub docId/qvtRequestId/SKU의 실제 접수 대조는 여전히 남는다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`와 운영 전송 gate를 유지하며 전체 동일 구현이나 실제 접수 완료로 보고하지 않는다.
