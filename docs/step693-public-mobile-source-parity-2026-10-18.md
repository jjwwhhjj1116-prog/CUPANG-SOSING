# Step693 — 공개 URL 수집의 옵션 사진과 응답 상태 일치

2026-10-18 KST. 기준 `9c49f080f5bf83d748a2a14754962ab8df523741`. Step692에서 확인한 실제 SKU 사진 규칙을 사용자가 URL 입력 시 사용하는 공개 모바일 원문 경로에도 적용했다. 기존 작업 상품·운영 데이터·공유 Chrome·쿠플러스/Supplier Hub는 변경하지 않았다.

## 실제 URL 경로의 사진 연결

Step692 수정은 `parseAlibabaProduct`의 OpenAPI 후보 응답에 한정됐다. 공개 페이지와 SKU 원문을 사용하는 `parseAlibabaSkuProduct`에는 같은 연결 누락이 남아 있었다. 첫 두 옵션 속성에 사진이 없으면 `imageIndex`를 생략해 SEO 원문 사진 연결이 없고, 견적서는 공통 대표사진을 대신 사용했다. 따라서 최초 견적 사진 표시 실패로 표현하지 않는다.

공개 전체 모바일, SKU-only, Chrome 원문과 부분 모바일 원문은 같은 SKU 정규화 함수를 사용한다. 이 함수에서 첫 두 선택 속성의 사진 후보를 모두 정규화·보관하고 첫 후보를 대표사진으로 연결한다. 둘 다 없으면 이미 검증·등록한 상품 갤러리 첫 index0을 쓴다. 세 번째 이후 속성 사진은 대표사진 후보에서 제외하지만 모든 옵션명·색상·사이즈·정렬과 SKU/가격/MOQ/재고 원문 규칙을 유지했다.

이는 REA로 확인한 쿠플러스 실제 SKU 처리의 첫 속성 → 둘째 속성 → 첫 상품 사진 규칙을 같은 의미의 공개 원문 속성에 적용한 것이다. 원본 대조의 관찰·추론·미확인은 [초기 문서 및 이미지 대조](step693-initial-document-parity-audit.md)에 구분한다. 정적 관찰을 실제 공급자나 비공개 수집 서버의 실행 증거로 확대하지 않는다.

유효하지 않은 첫 두 사진 후보는 선택되지 않았더라도 조용히 버리거나 갤러리로 대체하지 않는다. HTTPS Alibaba CDN 허용 목록과 크기·수량 제한을 유지한다. 갤러리와 같은 원본 URL은 index를 재사용하고 상세 역할은 별도로 보관한다. 옵션 축이 없는 경우도 명시적으로 제공된 실제 SKU와 빈 조합이 있어야 하며, SKU가 없는 원문에 가짜 옵션을 만들지 않는다. 수동 사진·공란·기존 번역 provenance와 제외 옵션을 덮는 새 후속 규칙을 넣지 않았다.

## 서로 모순되는 응답 상태

기존 공개 SKU 요청과 파서는 `ret` 중 하나만 SUCCESS면 전체를 성공으로 취급했다. 검증용 정상 데이터에 `SUCCESS`와 `FAIL_SYS_USER_VALIDATE` 또는 `FAIL_SYS_SESSION_EXPIRED`를 함께 넣으면 요청과 파서 모두 SKU를 반환하는 것을 격리 재현했다. 실제1688 공급자가 이런 혼합 응답을 보냈다는 사례는 확인하지 않았다.

새 `alibabaMobileResponseSucceeded`를 두 경로에서 공유한다. 상태 목록이 비어 있지 않고 모든 항목이 문자열 SUCCESS 상태일 때만 상품 사실을 수용한다. 성공 항목이 다른 인증·접근·재시도 오류를 숨길 수 없다. 토큰 준비 응답은 기존처럼 단일 `FAIL_SYS_TOKEN_EMPTY`일 때만 한 번 허용하며 혼합 상태나 반복 실패로 새 요청을 추가하지 않는다. 서버와 생성된 확장 번들에서 같은 판정을 사용한다.

이는 실제 사이트의 로그인·확인 화면을 우회하는 변경이 아니다. 외부 수집 성공을 만들어 내거나 기존 실패 원문을 성공으로 바꾸지 않았다. 원문 수신·초안 저장과 Supplier Hub 최종 접수도 구분한다.
