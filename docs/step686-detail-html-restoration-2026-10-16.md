# Step686 — 상세 저장 전 사진·견적 HTML 함께 재편집

2026-10-16. 기준 커밋 `f61139eb565709bcd32180d88c2f27b448809e1d`.

## 변경 결과

상세 이미지를 한 장으로 합쳐 전체 저장하면 최종 견적에는 통합 PNG와 빈 HTML이 연결된다. 이번 변경은 그 직전 선택 옵션의 **유효 견적 HTML 문자열**을 기존 순서 있는 입력 사진 백업과 함께 보관한다. 새 `저장 전 사진·HTML로 편집` 버튼은 실제 보관 파일과 현재 회사·상품·카테고리 연결을 읽어서 검증한 뒤 사진과 HTML을 함께 새 수동 초안에 넣는다. `선택 옵션 이미지 저장`을 누르기 전에는 저장된 견적을 바꾸지 않는다.

HTML의 수동 공란, 공백, 줄바꿈, 탭을 그대로 보존한다. 당시 옵션에 값이 없었는지(`null`), 공통 HTML을 상속했는지, 명시 문자열이 있었는지도 백업에 남긴다. 재편집은 당시 표시 문자열을 새 수동 초안으로 가져오는 기능이며 과거 상속 관계로 되돌리는 기능은 아니다. HTML은 텍스트로만 다루고 실행하지 않는다. 과거 저장본에 HTML 보관 증거가 없으면 임의로 생성하거나 다른 상품의 HTML을 가져오지 않는다. 기존 `저장 전 개별 사진으로 편집` 기능은 유지한다.

## 구현 연결

- 일반 상세 저장에 선택적 `editorPolicy: ordered-inputs-html-v1`을 추가했다. 화면은 새 정책을 명시하고, 기존 정책 없는 요청의 본문·업로드 식별·응답 계약은 유지한다. 최종 PNG 생성과 이미지 업로드 식별 알고리즘은 바꾸지 않았다.
- 서버가 현재 선택 옵션의 연결된 HTML 필드·읽기 권한·길이·승인 회사·정확한 카테고리 문맥을 확인하고 `detail-editor-snapshot-v1`과 정규 SHA를 만든다. 클라이언트가 주장하는 과거 HTML을 그대로 백업하지 않는다. 기존 원자적 견적/상품/백업 저장과 이력·용량 한도를 사용한다. 새 DB 테이블·마이그레이션·HTML R2 파일은 없다.
- `GET detail-save?editor=saved-composition-v1&optionId=…`는 동일 상품의 일반 저장본만 읽는다. 출력 PNG와 모든 입력 사진의 실제 SHA·표시 치수·용량, 현재 옵션·회사·문맥·저장 상태를 확인한다. 다른 상품에서 복사한 가족 사진 문서는 HTML 복원 권한으로 취급하지 않는다.
- 클라이언트는 정확한 9개 현재 출처 필드와 전체 응답을 검증한다. 사진 실제 바이트 검증 전후에 구성을 두 번 읽고, 이미 있던 전체 견적 재검증도 유지한다. 실패 시 사진·HTML 중 일부만 반영하지 않는다. dirty 입력, 다른 작업 진행 중, 오래된 핸들러·단계/옵션 ABA, 중복 클릭·언마운트는 기존 보호를 공유한다.
- 새 정책 저장·재확인 응답은 동일 정책과 snapshot SHA가 일치해야 성공이다. 응답을 잃으면 GET으로만 확인하며 자동 재업로드·재저장하지 않는다. 서버 재확인도 실제 파일을 읽는 동안 정확한 견적 원문과 회원 연결이 바뀌지 않았는지 확인한다. 일부 손상된 새 문서를 구형 문서 없음으로 낮추지 않는다.

`inputFingerprint`가 수동 HTML 문자열 자체를 직접 해시한다고 주장하지 않는다. 일반 수정 시 상품 시각이 바뀌며, 이번 저장은 별도로 정확한 견적 revision/원문 CAS와 snapshot digest를 확인한다.

## 검증

관련 24개 테스트 파일에서 고유 296개 통과. 최초 전체 실행은 292개 통과·4개 실패였고, 원인은 기존 수동 편집 테스트의 승인 응답과 실제 빈 `members` 테이블 간 불일치였다. 로컬 fixture에 실제 승인 회원을 넣고 PNG와 불변 편집 문서 2개 및 연결 SHA 검증을 추가한 뒤 그 파일 전체 6개를 다시 실행했다. 중복 집계 없이 기존 다른 290개와 최종 6개를 사용한다. 앱의 회원/원자적 저장 보호를 완화하지 않았다.

검사 기록:

- `outputs/step686-final-tests.log`, `outputs/step686-final-test-files.json`, 수동 편집 재검사 manifest.
- 전체 타입 검사, 변경 소스·테스트 lint, 스키마 검사, 운영 빌드 통과.
- 스키마는 43 tables / 17 indexes / 28 runtime modules이며 fresh/repeated 메모리 검사만 했다. 운영 DB에 마이그레이션을 실행하지 않았다.
- `outputs/step686-native-verified.json`: 실제 Chrome의 격리 React 화면·Canvas·실제 API·SQLite/R2 검사. 회사별 6개 옵션(제외 옵션 1개 포함), 원본 25개 파일과 메타데이터, 다른 41개 테이블 불변. 전체 저장으로 실제 800×290 PNG 1개를 추가하고, 읽기 전용 복원 후 선택 옵션만 사진 3장과 원문 HTML로 명시 저장했다.
- 와이홉은 공통에서 상속한 HTML, 유앤채는 ` \n\t ` 원문을 확인했다. 유앤채는 실제 저장 완료 후 응답 503을 의도적으로 주입하고 GET 1회로 복구했으며 저장 POST는 반복하지 않았다. 총 HTTP 92회=GET 86/POST 4/PUT 2, 정상 91/의도된 503 1. 각 회사 구성 GET 2회, 기존 작업 상품·외부 provider 쓰기 0.
- 검수 페이지의 최초 seed 버전이 고정되어 와이홉 새로고침 직후 오래된 버전 조회는 안전하게 차단됐다. 검수 회사 선택으로 서버의 최신 부모 버전을 다시 열어 영속화를 확인했다. 최초 새로고침 자체가 성공했다고 표시하지 않는다. 앱 소스/검수 서버는 시작 시 SHA와 동일하다.
- DOM 원문과 실제 요청·전체 테이블·파일 hash 증거는 보관했다. CDP 화면 캡처는 두 방식 모두 5초 시간 초과로 이미지가 생성되지 않았다. `screenshotsComplete:false`이며 화면 캡처 완료로 표시하지 않는다.
