# Step736 — 같은 견적서의 반려 항목·사유 보관과 표시

사용자가 요청한 카테고리 → 1688 URL → 1~7단계 → 수정 → Supplier Hub 전송 흐름의 후속 보완이다. Step735가 남긴 원본 표시 차이를 구현했다. 기존 작업 상품, 옵션, 이미지, 기본설정, 대기열과 Hub 견적서는 수정하지 않았다.

## 원본 근거와 구현

보관된 Hub `K4`는 선택한 등록 요청의 `remark` JSON에서 `errors[].columnName/message`를 읽어 표로 보여준다. Step735의 REA 기록을 재사용했으며 새 producer, vendor 코드 실행, 새 사이트 수집은 하지 않았다.

- 원본: `outputs/step548-hub-main.js`, SHA-256 `6fc9c0fae51702e62e2d1376ac8854d0d97c0035b0bf96afeb42069c2a5abe11`.
- remark 소비 범위: `[4154614,4154848)`, slice SHA-256 `8ef54602d5f519b8828c0d468cc6d31d30ce139dc0b6d78c1da4864a0d6b5f04`.
- 기존 parent: `ev_7bccb57e05307a52efc7ae3b1f8a61f5f96ef3cd32e29faeaf569b4b78483157`. 원본 wire 응답의 현재 형식·내용이나 실제 반려 발생을 새로 관측한 근거는 아니다.

`rejection-details.mjs`를 통해 이미 회사·문서·본문·등록 파일 ID가 일치한 REJECTED 행의 부가 진단만 정규화한다. 알려진 항목명·메시지를 순서대로 보관하고 정확히 같은 쌍만 중복 제거한다. JSON 오류, 누락, 비문자열, 제어문자, 32행/항목명 200자/메시지 2,000자/결과 32KiB 초과는 사유 미확인으로 표시한다. remark 입력 자체는 256Ki 문자 이하만 파싱한다. 부가 진단 실패가 별도로 확인된 반려 접수를 지우거나 성공·SKU 증거로 바꾸지 않는다.

Single과 전체 상품 문서의 receiver, 클라이언트, 서버 모델에서 선택적인 명시 계약을 검증한다. 이전 기록에는 이 필드가 없어도 된다. REJECTED 외의 상태에 반려 상세를 붙이거나, 알 수 없는 키·getter·희소 배열 등을 전달하면 거부한다.

DB의 기존 JSON payload에 보관하므로 마이그레이션은 없다. 진단 갱신은 문서·회사·본문·멤버의 불변 연결값을 바꾸지 않는다. 최신 관측 뒤 예전 저장 응답을 재시도해도 같은 문서의 최신 기록을 돌려주고, 다른 문서/등록 파일 ID나 반려→성공 전환은 기존 검증으로 거부한다. 진단은 재전송 허가나 새 동의의 근거가 아니다.

현재 전송 결과와 이력 양쪽에 ‘항목 / 반려 사유’ 표를 표시한다. React의 일반 텍스트로 렌더링해 HTML은 실행하지 않는다. 상세가 없으면 기존 Hub 확인 안내를 유지한다. 기존 작업 상품을 열어 수정하거나 샘플 반려 기록을 운영 DB에 넣지 않았다.

## 남은 실제 검증

새 1688 원문 수집, 최종 native POST/ACK, 새 docId→qvtRequestId와 SKU 연결은 미검증이다. Step732의 사이트 안전 거절을 재시도하거나 다른 수단으로 우회하지 않았다. `SINGLE_DOCUMENT_LIVE_VERIFIED=false`, `PRODUCT_DOCUMENT_LIVE_VERIFIED=false`를 유지한다. 기존 상품의 상태나 로컬 합성 접수 결과를 새 실제 접수 성공으로 보고하지 않는다. 따라서 전체 작업의 완성 또는 100% 달성을 주장하지 않는다.
