# Step 648 — 최종 견적서 패키지 대조와 전송 화면의 계정 분리

1~7단계에서 저장한 최종 값이 공식 Excel과 Chrome 첨부 자료에 그대로 연결되는지 확인하고, 그 과정에서 재현된 두 계정 전환 문제를 수정했다. 기존 운영 상품·수집 원문·쿠플러스 작업 자료를 수정하지 않는다.

## 최종 값과 원본 Excel

기록된 `Single69900v188` / `original2624.xlsx` 계약으로 양사의 격리된 합성 상품을 만들었다. 각각 6개 옵션의 SEO 상품명, 검색어, 옵션 원가와 최종 가격, 대표·추가·상세·사이즈·라벨 이미지, 표시사항, 수동 상세 HTML과 7단계 직접 입력을 실제 API·SQLite로 저장했다. 와이홉 fixture는 기록된 유앤채 계약을 재사용했으며, 새 와이홉 공식 다운로드나 실제 상품 수집 검증은 아니다.

원본 Excel의 9행부터 2열 제목, 11열 모델, 18/50열 재질, 23~28열 이미지·HTML·사이즈·대체 문구, 29~31열 가격, 33열 제조사, 47열 라벨을 최종 저장값과 대조했다. 한국어 옵션명 자동 제목 연결, 첫 옵션의 직접 제목, 다른 옵션의 직접 모델 공란과 MPN 공란이 유지된다. 전송 패키지는 각각 상품 이미지 5개·라벨 1개이고, 모든 최종 파일명·실제 첨부 바이트·SHA-256이 일치한다.

실제 확장의 `prepareAttachments`, 앱 `quotation action:source`, `handoff-content`와 `verifyAppQuotationSource`로 승인 회사·카테고리·지문 연결을 확인했다. 다른 회사와 다른 지문은 거절한다. 준비 과정에서 상품·원문·가격·설정·양식·원본 이미지·원본 Excel 바이트를 변경하지 않는다. 외부 요청, Hub 첨부·동의·전송, 접수 기록 생성은 모두 0이다. 증거는 `outputs/step648-final-package-proof.json`에 보관한다. 이 양사 검수 2건은 자동 시험 건수에 중복 합산하지 않는다.

기존 단일 SKU 전송 시험에는 이전 자동 제목 기대값이 남아 있었다. 이를 쿠플러스 옵션명 연결 계약으로 수정했고, 패키지에서 실제로 전달하는 XLSX를 다시 읽어 제목·가격 3개·이미지 4개·상세 HTML·포장 무게·크기가 미리보기와 일치하는지 검사했다. 1단계 SEO의 저장된 기본 제목은 옵션명을 덧붙여 변경하지 않는다.

## 전송 화면의 계정 전환

정상 상품·양식 변경은 기존 key로 검토/패키지 화면을 다시 만들지만, 대시보드 회원 변경에는 그 경계가 없었다. 견적서 준비 후 회원이 바뀌어도 이전 회사의 미리보기·동의 화면과 직접 전송 대상이 남는 동작을 실제 컴포넌트로 재현했다. 이것은 이전 회사 UI 노출의 재현이며 다른 회사에서 실제 전송이 성공했다는 증거는 아니다.

등록 전송의 의도를 회원 context 객체와 새 화면 session 객체에 묶었다. 회원 변경 렌더에서 이전 전송 화면을 즉시 제외하며, 닫기·수정·접수 후 목록 갱신 콜백도 그 session과 context가 현재 것인지 확인한다. A→B→A로 돌아오거나 같은 상품 ID가 있어도 예전 화면을 되살리지 않는다. 선택 상품도 현재 owner 소유 자료로 제한한다.

검토 요청과 패키지 요청은 layout cleanup에서 즉시 중단한다. 이전 passive cleanup과 오래된 finally가 새 요청 controller를 지우지 않도록 identity를 확인한다. 결과 추적의 일시정지 버튼도 렌더 당시 controller와 mounted 상태를 확인해 종료된 화면의 콜백이 새 요청을 취소하거나 state를 갱신하지 않는다. 기존 상품·양식 변경 key와 미저장 입력 보호는 유지한다. hook 시험 도구의 `useMemo`를 실제 deps identity로, `useLayoutEffect`를 실제 cleanup 순서로 보정했으며 기존 검증값을 완화하지 않는다.

## 접수 관찰의 승인 회원 확인

접수 결과의 source/회사 검사 후 마지막 DB 저장 직전에 승인 회원 정보가 바뀌면 이전 회사 결과가 저장되는 경계를 재현했다. 정상 저장과 원래 견적서의 역사 관찰 모두 저장 직전에 현재 owner·승인 회사를 다시 확인한다.

기존 회원 로그인이 활성화된 운영 환경에서는 그 회원의 id·이메일·역할·회사코드·회사명을 승인 snapshot으로 전달한다. D1의 INSERT·역사 UPDATE와 동일/오래된 관찰의 fallback SELECT 안에서 현재 `members`의 승인 상태와 그 snapshot을 원자적으로 비교한다. 승인 취소, 회사 변경, 이메일/역할 변경 또는 snapshot 누락/다른 회사 전달은 실패한다. 조회 GET·전체 이력·접수 ID 고정·관찰 순서·원본 보존과 개발 환경의 기존 저장 계약은 유지한다.

이 시험은 실제 `sessionMember`와 임시 SQLite의 회원·세션을 사용한다. 승인 회원 정상 저장/중복 읽기/역사 관찰, SQL 직전 상태·회사·이름·이메일·역할 변경, 정상/역사 fallback 경계를 양사에서 확인했다. 외부 등록이나 신규 권한 부여는 실행하지 않는다.

## 검수 및 배포 기록

중복 없는 14개 시험 파일 **225/225** 통과했다. 견적서 준비·검토 73, 대시보드·계정별 전송 69(신규 8 포함), 기존 접수·이력 복구 49, 실제 승인 회원 20, 법적 서류 첨부 14개다. TypeScript 오류 0, ESLint 오류 0·기존 경고 8, 최종 운영 빌드 검사를 확인했다.

같은 Chrome에서 실제 React 대시보드·검토·패키지를 사용한 로컬 합성 검수도 진행했다. 와이홉·유앤채의 준비된 견적 미리보기 2건과 지연 준비 2건을 각각 열고 4회 회원 context를 전환했다. 이전 검토창과 패키지가 없어지고 두 지연 요청의 client AbortSignal이 발생하며 SQLite·원본 파일은 유지된다. 원본 검수기의 엄격한 HTTP 종료 항목은 7/8로 보관한다. 취소 신호 후 owner commit ACK로 응답을 풀 때 서버의 정상 응답 완료가 먼저 기록될 수 있어 물리 연결 종료는 관측하지 못했다. 이를 통과 항목으로 바꾸거나 실제 외부 요청 취소 성공으로 해석하지 않는다. `native-verification.json`은 검증된 UI 분리·client 신호와 이 미관측 항목을 구분한다.

Worker `sourceflow`의 `80a9d46b-4cc5-40ba-880d-d8aa48f92ee3` 배포를 완료했다. 운영의 기존 상품 1개 행·등록 입력, 기본설정 35개, 수집 대기열, 상품관리 입력·행을 배포 전후 대조했다. 최종 JavaScript 자산을 실제 페이지 자산 목록에서 확인하고 운영 화면을 저장했다. 로그인·운영 상품·회사 기본설정을 다시 저장하지 않았다.

결과는 `outputs/step648-*`에 기록한다. 확장 0.2.64와 기존 공개 ZIP·권한, 19개 마이그레이션을 유지하며 신규 마이그레이션은 없다. 전체 카테고리 동등성이나 신규 실상품 1688부터 Supplier Hub 최종 접수까지 완료했다고 표시하지 않는다.
